    ADR-0012: Observability Consolidation

    Status

    Accepted (2026-04-27 — Linear ARUN-539)

    Context

    The SDK shipped two custom HTTP/observability surfaces and a sprawling seven-interceptor stack on the Temporal worker:

    • Server side — a hand-rolled MetricsMiddleware plus a custom Prometheus /metrics endpoint, recording http_requests_total / http_request_duration_seconds keyed by raw path (unbounded cardinality).
    • Worker side — ExecutionContextInterceptor, CorrelationContextInterceptor, Temporal's TracingInterceptor (gated), AppVitalsInterceptor, OutputInterceptor, EventInterceptor, and TaskFailureLoggingInterceptor, each with bespoke wiring and ContextVar dependencies.
    • "Metrics" emitted as App Vitals structured logs (with bespoke metric_name / dimension / app_vitals=true filter flag) indexed downstream in ClickHouse rather than as real OpenTelemetry instruments — un-scrapable by Prometheus and not aggregatable like normal metrics.
    • Temporal SDK's Rust-core Prometheus endpoint already wired (port 9464) but exposed as a second scrape target, undocumented and externally reachable.
    • Production supports Prometheus for metrics, OTLP for logs, no traces yet. Workers in this SDK are short-lived (per-job pods) and Prometheus may never scrape them before they exit.

    Decision

    Server side

    • Replace MetricsMiddleware with opentelemetry-instrumentation-fastapi. HTTP metrics now use the stable OTel HTTP semantic conventions (http.request.method, http.route, server.address, network.protocol.version, http.response.status_code) — opt-in via OTEL_SEMCONV_STABILITY_OPT_IN=http, which the SDK sets as a process default before instrumenting (an explicit value wins). The metric http_server_duration_milliseconds is renamed to http_server_request_duration_seconds (unit corrected from ms → seconds; matches the upstream-recommended base unit). Route templating eliminates the path-cardinality blow-up.
    • Rewrite the /metrics endpoint to merge two sources into one response: the OTel PrometheusMetricReader registry and the Temporal Runtime's loopback Rust-core endpoint. Operators get one scrape target per server pod.
    • Bind Temporal Runtime to 127.0.0.1:9464 so the second port is not externally reachable.

    Resource-attribute enrichment (inline on every series)

    EnrichedPrometheusMetricReader injects a single OTel resource attribute (app.name) onto every metric series so PromQL can filter by connector identity without a target_info join:

    Label (Prometheus) Source (OTel)
    app_name app.name

    The inline set is deliberately minimal. Per-release attributes (app.version, app.release_id, app.sdk_version, app.release_channel) are NOT inlined — they cycle on every deploy / channel promotion and would multiply indexdb cardinality across the metrics retention window. Apps that need to filter or group by these attributes use a query-time join against target_info (which carries the full Resource as a single info gauge per pod).

    The same single-key enrichment is mirrored onto Temporal Rust-core metrics via TelemetryConfig.global_tags, so the temporal_* families match the rest of the surface.

    Worker side — 7 interceptors → 3

    • LogInterceptor — emits four lifecycle log lines per execution (workflow.started, workflow.ended, activity.started, activity.ended) with OTel semantic-convention attributes; sets the ExecutionContext and CorrelationContext ContextVars; propagates x-correlation-id across activity / child-workflow boundaries via Temporal headers; logs activity failures with full exception.* / atlan.exception.* fields.
    • MetricsInterceptor — emits real OTel counters and histograms (temporal.workflow.executions, temporal.workflow.duration, temporal.activity.executions, temporal.activity.duration, temporal.activity.errors) via the global MeterProvider. Workflow-level samples are per run, not per workflow-instance lifetime: the interceptor instruments every lifetime (including one that enters replaying after an eviction or worker change), emits only when the run finishes live (is_replaying() false at exit, which excludes eviction teardown), and measures duration on the run's history clock (FND-5217).
    • TraceInterceptor — thin wrapper around temporalio.contrib.opentelemetry.TracingInterceptor, gated on ATLAN_ENABLE_OTLP_TRACES (default off, since production doesn't yet support traces). When on, run_main installs the global TracerProvider (OTLP only; a console exporter only behind the dev-only ATLAN_ENABLE_TRACES_CONSOLE) the upstream interceptor emits through.
    • @observability and AtlanTracesAdapter stay, because about 20 connector apps decorate functions with them. Since FND-4913 the adapter is a thin span emitter. Each record_trace becomes one span on that same global provider, timed from the operation's start to its end and parented to the current span. Nothing is buffered, flushed or written to the object store: those trace files had no reader, and building the adapter started a flush task on whatever loop built it.
    • Product-feature interceptors stay separate — OutputInterceptor (UI artifacts merged into workflow output) and EventInterceptor (v3 audit / dashboard event bus) are not observability and remain their own interceptors gated by their own settings. OutputInterceptor carries each activity's metrics and artifacts back to the workflow on the activity's own result (the metrics / artifacts fields of Output, or a reserved _atlan_outputs key on a dict result), not through process memory, so they survive an activity running on another replica or pool queue and a workflow replay on another worker.

    Pushgateway for short-lived workers

    • Worker-only deployments push to ATLAN_PROMETHEUS_PUSHGATEWAY_URL via PushGatewayClient (periodic + final-on-shutdown).
    • A TemporalCoreCollector registered with prometheus_client.REGISTRY feeds Temporal Rust-core metrics into the push so we don't lose scheduling / cache / poller signals on workers.
    • Combined deployments (server + worker in one process) leave the pusher off — /metrics already covers everything via in-process proxy and pushing would double-count.
    • Multi-pod safety: hostname-keyed grouping prevents cross-generation overwrite.
    • DELETE_ON_SHUTDOWN defaults to true — graceful exits drop their group from the gateway, no leak. Pushgateway has no built-in TTL, so without this every pod ever scraped leaked its series until manually deleted.
    • Startup sweep: every new worker pod, before its first push, reaps any stale {job=mine, instance=other} groups left by predecessors that died ungracefully (OOM kill, eviction, SIGKILL, node loss — cases where DELETE_ON_SHUTDOWN doesn't fire). Four safety guards: strict job-equality, skip own grouping_key, threshold gate (default 300s — protects live siblings during rolling deploys), per-group soft-fail. Runs once on startup; never blocks the periodic loop.
    • Bounded HTTP timeout (default 10s, env ATLAN_PROMETHEUS_PUSHGATEWAY_HTTP_TIMEOUT_SECONDS) on every gateway call (push, sweep GET, sweep DELETE, final push, final DELETE). Without this, a downed gateway would burn the prometheus_client default 30s × 2 calls at shutdown and exhaust Kubernetes' terminationGracePeriodSeconds. (Amended by FND-4645: the timeout is derived from ATLAN_SHUTDOWN_GRACE_SECONDS when that is set.)
    • Metrics is best-effort, never blocks the worker. _start_metrics_push is wrapped in try/except at the worker's __aenter__ / run() boundary so any unexpected metrics failure cannot prevent the worker from accepting Temporal tasks.
    • Pre-DELETE delay (default 35s, env ATLAN_PROMETHEUS_PUSHGATEWAY_SHUTDOWN_DELETE_DELAY_SECONDS) holds the group in the gateway between the final push and the DELETE_ON_SHUTDOWN call so Prometheus has at least one scrape window to read the final batch. Without it, the DELETE fires within milliseconds of the push and Prometheus' next scrape finds nothing — the last interval of metrics (often the failure increments that triggered the scale-down) would be lost. The default of 35s is one full 30s scrape interval (the cluster's vmagent default applied to the Pushgateway scrape — confirmed by inspecting the rendered vmagent.env.yaml) plus a 5s jitter buffer. (Amended by FND-4645: the original note assumed a 12h terminationGracePeriodSeconds. Not every deployment has one; SDR installs can run with 30s. The hold now runs under the post-drain exit deadline, and it is derived from ATLAN_SHUTDOWN_GRACE_SECONDS when that is set, so it shrinks with a short grace.)

    App Vitals

    Deleted. Replaced by the four lifecycle log lines emitted from LogInterceptor. ClickHouse views filter on the log body / event name (workflow.started, workflow.ended, activity.started, activity.ended) and project the old "dimension" categorisation (reliability / efficiency / throughput / performance) at query time from otel.status_code, temporal.*.duration_ms, and event count. Per-event dimension and app_vitals=true attributes are gone.

    The efficiency numbers survive as OTel histograms from MetricsInterceptor: temporal.activity.cpu_seconds and temporal.activity.mem_gib_seconds. They are process samples split evenly across the activities in flight, so they sum to the process total under concurrency (see Monitoring).

    Custom user metrics

    New module application_sdk.observability.metrics re-exports the global OTel meter for app authors:

    from application_sdk.observability import metrics

counter = metrics.create_counter("myapp.requests", description="...", unit="1")
counter.add(1, {"endpoint": "/foo"})

    Writes through the same MeterProvider as the SDK's interceptors, so user metrics appear in the FastAPI /metrics proxy on servers and ride along with the Pushgateway push on workers.

    Local parquet sink

    The Hive-partitioned *.json.gz sink + object-store upload stays — load-bearing for customer-environment archival. Local cleanup was already in a finally: block, so files don't leak even on short-lived workers. The DuckDBUI class (port 4213) is removed; it was a dev-workstation convenience and unused in production.

    Env var sweep (no backwards compat)

    Removed: ATLAN_ENABLE_APP_VITALS, ENABLE_PROMETHEUS_METRICS, ATLAN_ENABLE_PROMETHEUS_METRICS (renamed to ATLAN_ENABLE_TEMPORAL_CORE_METRICS), ENABLE_OTLP_METRICS, ENABLE_OTLP_TRACES (consolidated to ATLAN_ENABLE_OTLP_TRACES), METRICS_* (batch / flush / retention / cleanup), TRACES_* (batch / flush / retention / cleanup), enable_correlation_interceptor.

    Retained: ENABLE_OTLP_WORKFLOW_LOGS and OTEL_WORKFLOW_LOGS_ENDPOINT gate an optional secondary OTLP log exporter that ships logs to an archival collector (e.g. one writing to S3) in parallel with the primary OTEL_EXPORTER_OTLP_ENDPOINT pipeline. They were briefly removed in this consolidation but restored once we confirmed the production chart wires up an S3-archival collector that depends on this dual-export.

    Added: - ATLAN_ENABLE_TEMPORAL_CORE_METRICS (default true) — replaces ATLAN_ENABLE_PROMETHEUS_METRICS; gates only the Temporal Rust-core loopback bind, not the FastAPI /metrics route. - ATLAN_TEMPORAL_CORE_METRICS_PROXY_TIMEOUT_SECONDS (default 5.0) — per-request timeout for the in-process FastAPI /metrics proxy that fetches Temporal Rust-core series. - ATLAN_PROMETHEUS_PUSHGATEWAY_URL (no default — opt out by leaving unset) - ATLAN_PROMETHEUS_PUSHGATEWAY_INTERVAL_SECONDS (default 30) - ATLAN_PROMETHEUS_PUSHGATEWAY_DELETE_ON_SHUTDOWN (default true) - ATLAN_PROMETHEUS_PUSHGATEWAY_SWEEP_STALE_ON_START (default true) - ATLAN_PROMETHEUS_PUSHGATEWAY_SWEEP_STALENESS_SECONDS (default 300) - ATLAN_PROMETHEUS_PUSHGATEWAY_HTTP_TIMEOUT_SECONDS (default 10) - ATLAN_PROMETHEUS_PUSHGATEWAY_SHUTDOWN_DELETE_DELAY_SECONDS (default 35) — sleep between final push and DELETE so Prometheus can scrape the final batch before the group is wiped (covers one full 30s cluster scrape interval + 5s jitter) - ATLAN_SHUTDOWN_DRAIN_DELAY_SECONDS (Temporal worker drain delay before transport teardown — see PR #1174)

    Consequences

    Breaking

    • Prometheus dashboards / alerts that reference http_requests_total, http_request_duration_seconds, or App Vitals attribute names (metric_name, dimension, app_vitals, error_cause_chain) need updating to OTel semconv (http_server_request_duration_seconds, http_server_active_requests, temporal_*_executions_total, temporal_*_duration_seconds, exception.type, atlan.exception.cause_chain, etc.).
    • ClickHouse horizon.app_vitals_events MV needs to filter on log body (workflow.started / workflow.ended / activity.started / activity.ended) instead of app_vitals="true", and its projected columns need to read OTel semconv attribute names. The "dimension" categorisation moves into the view.
    • The app_vitals.wf.summary aggregate event (total_activities, bottleneck_activity_type, circuit_breaker_tripped, etc.) is gone. The same data is derivable at query time from the four per-activity events.

    Operational

    • One scrape target per pod (/metrics on the server, Pushgateway-pushed for workers). Operators no longer need a second scrape config for port 9464.
    • Pushgateway sticky-data sharp edge: hard-killed worker pods leave their last-pushed values in the gateway forever. Mitigations: hostname-keyed grouping (no overwrite across generations) and the optional ATLAN_PROMETHEUS_PUSHGATEWAY_DELETE_ON_SHUTDOWN flag for graceful exits.

    Sequenced rollout

    1. atlan-app chart PRs (preprod / staging / beta lanes) ship first so clusters understand the new chart values that pair with this SDK release.
    2. This SDK PR ships next.
    3. global-marketplace auto-injection PR follows.
    4. ClickHouse views + Prometheus dashboards / alerts updated to read the new attribute / metric names.
    5. SDK consumer apps bump the dependency only after step 4 has merged into the environments scraping them.

    Alternatives considered

    • Keep the MetricsMiddleware and rename via aliasing. Rejected — doesn't fix the cardinality blow-up and keeps two parallel emitters.
    • Linger-and-scrape on workers (sleep scrape_interval + buffer before exiting). Initially picked, but workers are deliberately short lived — Pushgateway is the right shape for batch jobs.
    • OTel collector for metrics (single push pipeline shared with logs). Rejected for now: production doesn't yet have an OTel collector accepting metrics, and this would make worker startup depend on it. Direct Pushgateway push uses the existing TSDB.
    • Dual-emit window for old + new metric / attribute names. Rejected — hard cutover with consumer-side PRs shipping in the same release window.
    • Per-process OTel meter for Temporal core metrics (push via Temporal OpenTelemetryConfig instead of Prometheus). Rejected for the same OTel-collector reason; the loopback Prometheus + bridging collector pattern works without new infra.

    Addendum: one background loop for every periodic flush (FND-4648)

    The sinks used to start their periodic flushes three different ways: a task on whatever loop was running, else an asyncio.run thread (metrics, traces); a new_event_loop + run_forever thread (logs); a hand-built loop on a thread (sizing). The Segment client ran a fourth thread with its own loop and waited up to 5 s for it to come up. Each had its own cadence and its own shutdown, or none, so no single bound covered the final flushes at exit.

    Now application_sdk.observability.background_loop owns one daemon thread (atlan-observability-loop) running one event loop, started on first use. Every sink starts its periodic flush through AtlanObservability._start_periodic_flush(), always on that loop, and the Segment sender runs there as a task. One atexit shutdown, bounded by ATLAN_OBSERVABILITY_SHUTDOWN_TIMEOUT_SECONDS (default 10 s), cancels each started task once (its CancelledError handler makes the final flush or sends the last batch), awaits any other task on the loop without cancelling it (cancelling a batch flush deletes its half-written file), then stops the loop. Tasks stop in stages: the periodic flushes first, then the Segment worker, so the metrics final flush drains the Segment queue through an HTTP client that is still open. A cancel that arrives before a task's first step is deferred until the task has started, so its final flush still runs.

    The metrics and sizing sinks each run one periodic flush per class, and so does the logs sink when the object-store sink is on (ATLAN_ENABLE_OBSERVABILITY_STORE_SINK, default true). The first sink of the class starts it through AtlanObservability._ensure_periodic_flush(). The "flush started" guard is one per-class registry on the base, and _stop_class_flushes_for_testing() is the one test reset: it stops the periodic flush and every batch flush of every sink of the class, and releases the class (FND-4918). The logs, metrics and sizing sinks used to copy this bookkeeping each, and the logs copy's reset cleared the guard without stopping the flush.

    After fork(), the child replaces the loop's lock, forgets the parent's loop, drops each Segment client's worker, and restarts every sink's periodic flush on its own loop. Without that, the child inherits the "flush started" guards but not the thread, and nothing in it would flush.

    Two pieces of background work stay off the loop on purpose. The console writer is a plain thread because its job is a blocking write() to stdout; on the shared loop a stalled pipe would stall every flush. The OTLP exporter's batch thread belongs to the OpenTelemetry SDK.

    Addendum: retention of exported files belongs to the bucket, not the SDK (FND-4889)

    Decision. The SDK writes observability files to the object store and never deletes them. How long they are kept is set by a lifecycle rule on the bucket, owned by whoever owns the bucket. The SDK has no retention setting.

    What was removed. AtlanObservability carried a retention sweep (_check_and_cleanup / _cleanup_old_records), configured by ATLAN_{LOG,METRICS,SIZING}_RETENTION_DAYS and …_CLEANUP_ENABLED. It never deleted an exported file: it walked the pod's local partition tree, which is empty once each file is uploaded and unlinked; the key it deleted lacked the artifacts/apps/observability/ prefix every upload uses; and storage.delete removes one object, not a prefix. With cleanup on, it still cost a state-store read on every flush. The sweep is gone. The env vars are in _REMOVED_ENV_VARS (warn when set), and the constants and constructor parameters are deprecated aliases until v4.0.0.

    Why not fix it. A working sweep is the wrong design, not just a missing piece:

    • The prefix is shared. Uploads go to artifacts/apps/observability/{sdr|non-sdr}/<signal>/year=…/hour=…/, with no app or deployment segment; only the file name carries those. One app's retention setting would expire every other app's files under the same prefix.
    • Every pod would run it. Each worker of each app would list and delete across that shared prefix, racing the others on the same keys. A lifecycle rule does the same work once, inside the store, at no cost to the app.
    • The SDK does not own the buckets. Files go to the deployment (customer) store, and in SDR mode also to the upstream (Atlan) store. Deleting from either is the owner's decision, and the owner already has the tool for it. This matches ADR-0014, where customers set lifecycle policies on the artifact prefixes they hold.
    • Nothing depends on it. The sweep never deleted anything, so removing it changes no observable behaviour. Making it work would start deleting data across the fleet on a routine upgrade.

    If SDK-side retention is ever wanted, treat it as a new feature with its own ADR. It needs a per-app (or per-deployment) key layout, or a file-name filter, so one app cannot delete another's files; an explicit decision on the upstream store; and a single owner, such as one scheduled job, instead of every pod.
