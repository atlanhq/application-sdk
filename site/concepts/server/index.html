    Server (Handler Service)

    In v3, the HTTP server is created by the create_app_handler_service() function. This replaces the v2 APIServer class and its register_workflow() / HttpWorkflowTrigger pattern.

    Creating the Handler Service

    The handler service auto-wires routes from your Handler methods:

    from application_sdk.handler import create_app_handler_service
from my_package.handlers import MyHandler

app = create_app_handler_service(handler=MyHandler())

    When started (via the CLI --mode handler or --mode combined), this creates a FastAPI application with:

    • Routes for test_auth, preflight_check, and fetch_metadata derived from your Handler subclass
    • Health check endpoints
    • MCP server integration (if configured)

    Health Check Endpoints

    Every handler service exposes health checks at two equivalent paths each:

    Endpoint Method Purpose
    /health (alias: /server/health) GET Liveness probe
    /ready (alias: /server/ready) GET Readiness probe

    These are registered automatically. No configuration is needed.

    In combined mode, /ready returns the co-hosted worker's readiness. It sends the same body as the worker health port's /ready, and a 503 when the worker is not ready, so the two ports give the same answer about the pod. In handler-only mode it always returns 200 {"status": "ok"}.

    Worker liveness window

    In worker and combined mode the SDK also runs a WorkerHealthServer that exposes /health, /ready, and /live.

    Poll-loop checks (on by default)

    /live returns 503 when the worker is alive but its Temporal poll loop is confirmed dead (FND-4641). Kubernetes then restarts the pod, which recovers a worker that the in-process restart supervisor and fatal-teardown watchdog could not. Two conditions trip it:

    Condition Default Opt-out
    sdk-core's poller gauge reads a definitive zero for N consecutive observer readings N = 5 (about 5 minutes at the 60s interval) ATLAN_WORKER_LIVENESS_MAX_ZERO_POLLER_READINGS=0
    A fatal poll error is followed by no polling reading within the bound 600 seconds ATLAN_WORKER_LIVENESS_FATAL_RECOVERY_SECONDS=0

    The zero-poller check does not false-positive on an idle queue: an idle worker still reads its configured poller count. An unknown reading (gauge unreadable) resets the count rather than adding to it. The fatal check is cleared by the first polling reading after the fatal, which the supervisor produces when it rebuilds a worker that polls again. When the gauge cannot be read at all (Prometheus exporter or observer disabled), no recovery is visible, so a fatal restarts the pod after the bound even if the supervisor recovered in process. The 503 body carries the poller counts, fatal count and fatal_unrecovered_since for diagnosis.

    Import-wait check (on by default)

    /live also returns 503 when a thread has waited longer than ATLAN_WORKER_LIVENESS_MAX_IMPORT_WAIT_SECONDS (default 300) on the same module import lock (FND-5531). Temporal's deadlock interrupt (TMPRL1101) can land inside Python's import system and leave a module's import lock unable to wake its next waiter. That thread then waits forever while holding the lock of the module it was importing, so every later import of that module hangs in every thread, activities included, while the poll loop keeps polling.

    The check reads CPython's own record of which thread waits on which import lock (importlib._bootstrap._blocking_on). It starts no thread and imports nothing. A wait is timed from the first /live request that sees it. A healthy import, even a slow cold one, never waits this long. The 503 body names the module and the waiting thread, and the ERROR log adds where the stuck import chain was started (the outermost line that called into the import machinery) plus the thread's full stack. When that line is a function-local import in workflow code, the fix is to move it to module level; restarting the pod only stops the bleeding, and a cold, busy replacement can hit the same wedge. If a future Python changes that private table, the check logs one warning and stays healthy. Set the variable to 0 to disable it.

    Idle window (off by default)

    Setting ATLAN_WORKER_LIVENESS_MAX_IDLE_SECONDS to a positive value makes /live fail once no worker activity (an activity execution or heartbeat) has been recorded within that window, so a Kubernetes livenessProbe can recycle a worker whose Temporal poll loop has silently parked while run() never returns or raises (BLDX-1552) — the one failure the in-process restart supervisor cannot see.

    The window is disabled by default (0) because a positive value false-positives on legitimately idle queues, where no work arriving is normal rather than a stall. Enable it only for continuously-busy queues, and set it larger than the longest activity that runs without heartbeating so a slow but healthy activity is not mistaken for a parked poll loop. The probe never fails before the first activity is recorded, so it does not kill a worker during startup. See the env var in docs/concepts/common.md.

    Handler Method Routing

    The service maps your Handler methods to HTTP endpoints:

    Handler method HTTP endpoint Method
    test_auth() /workflows/v1/auth POST
    preflight_check() /workflows/v1/check POST
    fetch_metadata() /workflows/v1/metadata POST

    The service layer injects self.context into the handler before each request and clears it after. Your handler methods receive typed Input objects and return typed Output objects.

    Full Endpoint Reference

    All routes registered by create_app_handler_service():

    Endpoint Method Description
    /workflows/v1/auth POST Test authentication credentials
    /workflows/v1/check POST Run preflight connectivity checks
    /workflows/v1/metadata POST Browse source metadata (schemas, tables)
    /workflows/v1/start POST Start a workflow run (use ?entrypoint=<name> for multi-entry-point apps)
    /workflows/v1/validate POST Validate a workflow configuration against the entry point's published input contract, without starting anything. Also served by the consolidated API host (see Validating a workflow configuration)
    /workflows/v1/stop/{workflow_id}/{run_id} POST Terminate a running workflow
    /workflows/v1/result/{workflow_id} GET Fetch the final result of a completed workflow
    /workflows/v1/status/{workflow_id}/{run_id} GET Poll workflow execution status
    /workflows/v1/config/{config_id} GET Retrieve a workflow config (configmap)
    /workflows/v1/config/{config_id} POST Update a workflow config
    /workflows/v1/file POST Upload a file to the handler
    /workflows/v1/configmap/{config_map_id} GET Retrieve a configmap by ID
    /workflows/v1/configmaps GET List all configmaps
    /workflows/v1/manifest GET Retrieve the app manifest (supports ?entrypoint=<name>)
    /manifest GET Alias for /workflows/v1/manifest (for backward compat)

    /health, /server/health GET Liveness probe
    /ready, /server/ready GET Readiness probe
    /metrics GET Prometheus metrics (always exposed; merges SDK custom metrics + HTTP server instrumentation + prometheus_client defaults, plus Temporal Rust-core families proxied from 127.0.0.1:9464 when enabled and reachable)
    / GET API root / service info

    Validating a workflow configuration

    POST /workflows/v1/validate?entrypoint=<name> checks the body a workflow will be started with against the entry point's published input contract, then stops. That is the same model GET /workflows/v1/input-contract serves. Call it when a workflow is created, so a configuration the runtime cannot execute is rejected at submission instead of failing at engine time.

    It lives with the metadata routes, so it ships in atlan-application-sdk-api. The consolidated API host serves it from the app's generated contract, and so does the worker, which resolves the same contract. It needs no Temporal connection and no running worker.

    It goes further than the JSON Schema, because it also runs the contract's field_validators. For the SQL templates those reject:

    • SQL-unsafe filter values;
    • include/exclude/temp-table patterns that every engine the SQL templates target rejects (POSIX ERE, PostgreSQL, ICU, RE2, Java): an unterminated ( or [, a reversed character range, or a trailing backslash. Syntax that only some dialects accept (\p{L}, POSIX classes, a lone )) is left for the source to judge. The error names the field and position, never the pattern.

    workflow_id / workflow_type and inline credentials (v2 or v3 shape) are taken out before the contract judges the body, as /start does: credentials are never part of a workflow's configuration. Instead, the route checks credentials for the fields the app's own generated forms mark required per auth type (required = true on each FieldSpec in credentials.pkl):

    What the body carries Checked against 422 field
    Inline credentials, e.g. at credential creation The credential form, <credential-type>.json, for the selected authType (else the form's default), including its anyOf implications credentials.extra.atlan_oauth_id
    extraction_method: "agent" The workflow form's agent schema (agent-json → agentConfigs): every required field must map to a secret key agent_json.gcp-wif.extra.atlan_oauth_id, or agent_json when there is no populated spec
    A GUID-routed method (direct, …) The workflow form's credential slot: when it is required, the body must reference a credential (credential_guid, or any populated CredentialRef field) credential_guid

    Each check runs only when the form that governs it ships in generated/. A required field with a non-empty declared default counts as provided. A vault credential's stored values can't be read here, so send the credential inline when it is created to have its fields checked. A declared-source (format 2) agent spec is left to its own validation. Each gap is a pydantic missing error naming the field. No credential value is returned or logged.

    Outcome Status Body
    The body fits the contract 200 {"success": true, "data": {"entrypoint"}}
    The body does not fit the contract, or is not a JSON object 422 {"success": false, "message": "Invalid request: <fields>", "detail": [{"field", "message", "type"}]}
    Invalid ?entrypoint= name / several entry points and none named 400
    Unknown ?entrypoint= 404

    The 422 never includes pydantic's input, because the rejected value can be a credential. The SDK's own validators (SQL filters, regex structure, incremental markers, required credential fields) name the field and the problem, never the value. A custom validator in an app's contract is returned as written, so it must not put the value in its message either. /workflows/v1/start (worker only) answers the same 422 shape when its body does not fit the entry point's input type, before it touches Temporal.

    MCP Server Integration

    If your application exposes an MCP (Model Context Protocol) server, the handler service can integrate it. MCP endpoints are wired alongside the standard handler routes.

    CLI Usage

    In production, run the handler service as a separate pod:

    application-sdk --mode handler --app my_package.apps:MyExtractor

    For local development, --mode combined runs both the handler service and the Temporal worker in one process:

    application-sdk --mode combined --app my_package.apps:MyExtractor

    Programmatic Usage

    For integration tests or custom setups:

    from application_sdk.main import run_dev_combined
from my_package.apps import MyExtractor

import asyncio
asyncio.run(run_dev_combined(MyExtractor))

    Error Handling

    Handler methods signal errors by raising a typed AppError leaf from application_sdk.errors:

    from application_sdk.errors import AuthError
from application_sdk.handler import Handler

class MyHandler(Handler):
    async def test_auth(self, input: AuthInput) -> AuthOutput:
        if not valid:
            raise AuthError(message="Invalid credentials")
        ...

    The service answers with the HTTP status for the leaf's category (AuthError is 401; see Handlers for the table) and the redacted message as detail. HandlerError is deprecated (removal in v4.0).
