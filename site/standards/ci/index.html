    CI authoring standard

    Guidance for writing and changing GitHub Actions workflows in this repo.

    No conditional logic in inlined shell

    Rule: a workflow run: block must not contain conditional logic — if/else, loops (for/while), case, or non-trivial command chaining whose behaviour branches on state. The moment a step needs to decide something, that decision moves into a script.

    Where the logic goes: a script under .github/scripts/, written in Python (the established convention — see the existing drivers there), with a pytest beside it in .github/scripts/tests/. The workflow step then just invokes it:

    - name: Do the thing
  run: python3 .github/scripts/do_the_thing.py --flag "${{ inputs.flag }}"

    Inlined run: blocks are fine for straight-line commands — install a tool, curl a binary, git push, run a linter. The bar is specifically branching.

    Why: logic inlined in YAML cannot be unit-tested, so it regresses silently as the automation evolves. A script can be exercised against fixtures — success paths, failure/fallback paths, edge cases — so a refactor that breaks a branch fails a test instead of breaking production CI. It is also reviewable in isolation and reusable across workflows.

    Testability seam

    Side-effecting commands (pkl, git, ruff, network calls) should go through a single thin wrapper function so tests can stub the external tool and let the rest run for real. See .github/scripts/renovate_pkl_sync.py and its test (.github/scripts/tests/test_renovate_pkl_sync.py) for the pattern: pkl/uvx are stubbed, git runs against a throwaway repo in tmp_path, and every branch (opt-in gate, missing input, eval-failure fallback, no-change short-circuit) has a case.

    Call gh through _gh.py, write outputs through _gha.py (FND-4924)

    A new script does not write its own gh wrapper or its own $GITHUB_OUTPUT writer. Import the shared ones:

    Need Use What it decides for you
    Run gh _gh.gh(args, input=, timeout=, retries=, idempotent=) A timeout on every call (120 s default), retry with backoff on a transient failure, GhError(status, stderr) on any other
    Parse its JSON _gh.gh_json(args) A non-JSON answer is a GhError, not a crash
    Read a paginated REST listing _gh.gh_paginated(path, key=) --paginate --slurp plus one flatten; a page of the wrong shape is an error, not a silent drop
    Decide "worth retrying" _gh.is_transient(status, stderr) 5xx, 429, a rate-limit 403 (not a permission 403), network errors
    Set a step output _gha.set_output(name, value) / set_outputs({...}) Heredoc form with a random delimiter for any multi-line value; stdout when $GITHUB_OUTPUT is unset
    Write the step summary _gha.append_summary(markdown) Same unset behaviour

    Pass idempotent=False for a call that creates something (a POST of a check run, a comment, a ref). It is then retried only on a rate limit, which GitHub refuses before doing the write; a 5xx or a timeout may already have created the object, so a retry would leave a duplicate.

    Tests stub _gh.run, the one subprocess seam, and get the real retry, classification and parsing. The conftest sleep stub makes backoff free.

    Existing scripts adopt these incrementally (FND-4924 and its follow-ups). Two kinds of script must stay self-contained and not import them: one a workflow sparse-checks-out as a single file, unless the sparse set is widened in the same change, and one vendored into consumer repos (probe_code_scanning.py, build_conformance_args.py).

    Never aggregate over gh api --paginate --jq

    With --paginate, gh runs the --jq filter once per page. A filter that aggregates (length, add, first, any) therefore prints one result per page: a review count over two pages is "1\n0", not 1. Fetch the listing with _gh.gh_paginated (--paginate --slurp plus a flatten) and do the counting in Python. renovate_approval_conditions.fetch_reviews and count_signature_approvals do this for review counts, and vuln_auto_merge_gate imports them rather than keeping its own copy (FND-4898). A per-item filter such as .[].filename is fine, since its output does not depend on where the page boundaries fall.

    When two gate scripts do the same step, import one from the other. A fix to a private copy does not reach the other script.

    Enforced by a test (FND-4244)

    .github/scripts/tests/test_no_conditional_run_blocks.py walks every workflow under .github/workflows/ and every composite action.y*ml under .github/actions/ (which actionlint does not lint), and fails on any run: block that branches: an if/for/while/until/case/select in command position, or a test chained into the next command ([ … ] && x, test -n "$X" || { …; }). Comments, quoted strings and ${{ … }} expressions are blanked first (whole-line and trailing comments alike), and backslash continuations are joined, so prose in an echo does not count and a chain split across lines does. A heredoc interpreter (python3 - <<EOF) is scanned too: logic in it is still untested.

    Blocks that predate the guard are listed in .github/scripts/conditional_run_allowlist.txt, keyed <file>::jobs.<job>.<step id|name> (or ::runs.<step> for a composite action). Two checks keep it from growing:

    • An entry whose block is gone or no longer branches fails as stale, so a migration deletes its line in the same PR.
    • The entry count must equal ALLOWLIST_CEILING in the test. Removing an entry means lowering the ceiling in the same PR, so the ceiling only goes down.

    This is a shrinking size cap, not a frozen set. CI does not stop a PR that removes a migrated entry and adds a different one in its place at the same count. That shows up as an added line in the allowlist diff, and review should refuse it.

    A new step that needs to decide something gets a script, not an allowlist entry.

    Every job sets timeout-minutes

    Rule: every workflow job that runs steps: declares timeout-minutes below 360: a literal, or ${{ inputs.<name> }} naming a workflow_call input whose default is a literal below 360. In-repo callers may not pass that input 360 or more. A job that calls a reusable workflow (uses:) cannot take a timeout-minutes of its own; the called workflow's jobs carry it.

    Why: GitHub's default is 360 minutes. A job that waits on a run in another repo, or on a callback that never arrives, otherwise holds a runner and, on the merge queue, a queue slot for six hours.

    Choosing the value: a few times the observed duration (check recent runs), not the 360-minute default. When a step runs its own poll with a budget (poll_dispatched_run.py, poll_check_runs_gate.py), set the job cap above that budget, so the poller reports its own timeout instead of the job being killed without a verdict. flag_job_timeouts.py warns when a job finishes close to its cap, which is the signal a value is too low.

    .github/scripts/tests/test_job_timeouts.py enforces the rule over every workflow under .github/workflows/, and fails if a conformance bootstrap template grows a job with its own steps that it cannot parse.

    Running the script tests

    The CI script tests workflow (.github/workflows/scripts-tests.yaml) runs pytest .github/scripts/tests on every PR:

    uv run --frozen --extra workflows python -m pytest .github/scripts/tests -q

    If you add a new script, add its test in the same PR — the workflow will pick it up automatically.

    The suite has its own .github/scripts/pytest.ini, which pytest uses instead of the root pyproject.toml whenever its arguments sit under .github/scripts. Its pythonpath puts .github/scripts and .github/scripts/tests on sys.path, so a test imports its script with a plain import do_the_thing and a shared helper with from _workflows import …. Do not add a sys.path.insert for either directory; test_pytest_ini.py fails on one. A script kept elsewhere (.github/actions/*/, build_and_publish/) still needs its own insert.

    A test that asserts on workflow or composite-action YAML reads it through .github/scripts/tests/_workflows.py (load_workflow, job, steps, step_named, triggers) rather than declaring its own _load / _job / _step.

    The trigger is deliberately not path-filtered. Part of this suite consists of cross-file guards that read YAML outside .github/scripts/ — the mask-before-write call-site check below is one — and any paths: list would have to enumerate every file they inspect, so it would silently stop firing on exactly the edits those guards exist to catch. Don't add one; a sub-minute suite is cheaper than that failure mode. Because it concludes on every PR, both of its jobs are required checks on the main ruleset (pytest .github/scripts/tests and pyright .github/scripts), without the always-concluding-gate wrapper that path-filtered required checks need (see sdk-gate.yaml for that pattern). Renaming either job renames the required context: update the ruleset in the same change, or every PR waits on a check that never reports.

    pyright on .github/scripts: a baseline that only shrinks

    [tool.pyright] excludes .github/**, so the pre-commit pyright hook (the SDK-tree check below) never sees the CI scripts. The pyright .github/scripts job runs .github/scripts/check_pyright_baseline.py, which runs pyright over .github/scripts with the repo's own pyright settings (minus the exclude, pinned to Linux and the requires-python floor) and compares the result, per file and per rule, with .github/scripts/pyright_baseline.json:

    • A count above the baseline fails. Fix the new finding.
    • A count below the baseline also fails. You fixed something: lock it in.
    • A baseline count above the base revision's fails. CI passes --base-sha (the PR's base), so raising the baseline with --update to make room for a new finding does not get past the check. Two exceptions are handled explicitly: a renamed file carries its counts to the new path, and a PR that changes the pinned pyright version (recorded as pyright_version in the baseline, which must equal the dev pin) may raise counts. The increases are printed as warnings for the reviewer.
    uv run --frozen --extra workflows python .github/scripts/check_pyright_baseline.py           # check
uv run --frozen --extra workflows python .github/scripts/check_pyright_baseline.py --update  # rewrite baseline

    Counts are per (file, rule), so fixing one finding does not pay for a different new one in the same file. A new script starts at zero: it must be pyright-clean. A pyright upgrade (the dev-group pin, which both pyright pre-commit hooks run) may move counts either way; regenerate both baselines in that PR.

    The generated pyright config is written inside .github/scripts, not at the repo root. pyright auto-excludes **/.* below a config's root whatever exclude says, so a repo-root config can never reach .github/. If pyright reports 0 files analysed, the check fails rather than matching an empty baseline.

    pyright on the SDK tree: errors held to a baseline that only shrinks

    reportArgumentType, reportAttributeAccessIssue and reportFunctionMemberAccess are errors in [tool.pyright] (FND-4295). They were warnings, which pre-commit does not fail on, so an argument-type or attribute bug in new code passed CI; the findings that predate the promotion are held to the repo-root pyright_baseline.json. The pre-commit pyright hook runs check_pyright_baseline.py --scope sdk, the same check as above over everything [tool.pyright] includes, with two differences: it counts errors only (warnings stay advisory), and it runs in a venv with every extra and group installed, as CI's is. The same three outcomes apply. In CI, the Pre-commit Checks job (codeql.yaml) sets PYRIGHT_BASELINE_BASE_SHA to the PR's (or merge group's) base, which the check reads when --base-sha is not given, so both pyright hooks there also refuse a baseline raised in the same PR.

    uv run --frozen --all-extras --all-groups python .github/scripts/check_pyright_baseline.py --scope sdk           # check
uv run --frozen --all-extras --all-groups python .github/scripts/check_pyright_baseline.py --scope sdk --update  # rewrite baseline

    The base comparison is per rule, summed over severities, so promoting a rule from warning to error moves its findings to a new key without reading as new ones. The SDK baseline never held the warnings, so for it the check also reads the base revision's [tool.pyright]: a rule the base set explicitly to warning/information/none and this PR sets to error may raise its counts, printed as a ::warning:: for the reviewer. A rule the base left at pyright's default stays strict (it may already have been an error there). An unreadable base pyproject.toml fails the check.

    A PR that introduces a baseline (no baseline file at its base) is compared with pyright's findings on the base revision's own tree instead, checked out in a temporary git worktree and analysed under the PR's rule levels (the base's own enableTypeIgnoreComments / reportUnnecessaryTypeIgnoreComment, since its comments were written for them). So even the PR that adds a baseline cannot add a finding to it.

    # type: ignore is off (enableTypeIgnoreComments = false): it silenced every rule on its line, and the mypy codes in its brackets mean nothing to pyright. Suppress with # pyright: ignore[<rule>]. reportUnnecessaryTypeIgnoreComment is an error, so a suppression that outlives its finding fails the check.

    Conformance function size: a C901 / PLR0915 baseline that only shrinks

    packages/conformance measures ruff's C901 (McCabe complexity above 10) and PLR0915 (more than 50 statements) over conformance/, at thresholds pinned in its [tool.ruff.lint.mccabe] / [tool.ruff.lint.pylint]. Neither rule is in the package's ruff select: about 190 existing functions exceed them. They are held instead to packages/conformance/ruff_complexity_baseline.json, per file and per rule, by packages/conformance/tests/test_complexity_baseline.py, with the same three outcomes as the pyright baseline above:

    • A count above the baseline fails. Split the new or grown function. The failure lists every over-limit function in the file.
    • A count below the baseline also fails. Lock the improvement in with --update.
    • A baseline count above the base revision's fails. The Conformance Suite Tests job passes --base-sha. --update also refuses to raise a count unless given --allow-increase.
    uv run --frozen python packages/conformance/tests/test_complexity_baseline.py           # check
uv run --frozen python packages/conformance/tests/test_complexity_baseline.py --update  # lock in a reduction

    The file is both a pytest module (the package's own test run) and a script (the conformance-complexity-baseline pre-commit hook and the CI base check). It needs only ruff, which the root env pins to the package's version. A new file starts at zero, so new code must stay under both thresholds.

    Any in an SDK signature: an ANN401 baseline that only shrinks

    ruff's ANN401 flags typing.Any in a parameter or return annotation. It is not in the root ruff select: application_sdk/ had about 490 such sites when it was enabled (FND-4301). They are held instead to .github/scripts/ann401_baseline.json, per file, by .github/scripts/check_ann401_baseline.py, with the same three outcomes as the baselines above:

    • A count above the baseline fails. Type the new signature (see coding.md, "No Any in a signature"). The failure lists every site in the file.
    • A count below the baseline also fails. Lock the improvement in with --update.
    • A baseline count above the base revision's fails. The CI script tests job passes --base-sha; a file renamed in the PR keeps its base count. A base with no baseline file is measured on its own tree instead.
    uv run --frozen python .github/scripts/check_ann401_baseline.py           # check
uv run --frozen python .github/scripts/check_ann401_baseline.py --update  # lock in a reduction

    The baseline is the only suppression. ruff runs with --isolated, so it reads no config file: ignore, extend-ignore, per-file-ignores, extend-per-file-ignores, exclude, extend-exclude, a nested ruff.toml and flake8-annotations.allow-star-arg-any cannot hide a site. --ignore-noqa does the same for # noqa: ANN401. test_check_ann401_baseline.py writes each of those into a throwaway tree and asserts the sites are still counted. Because no config is read, the target version is passed explicitly and a test holds it to requires-python.

    The counts are per file, not per site. Swapping one Any for another in the same file leaves the count unchanged and passes; the ratchet stops a file's count from rising, and review is what catches a like-for-like swap.

    A tree with no ANN401 left passes: an empty measurement is accepted when ruff, run the same way, still flags a canary with a known Any signature. A ruff that stopped reporting the rule fails instead of matching an emptied baseline.

    The ann401-baseline pre-commit hook runs the check on every change under application_sdk/.

    SDK function size: a C901 / PLR0915 baseline that only shrinks

    ruff's C901 (McCabe complexity above 10) and PLR0915 (more than 50 statements) are not in the root ruff select: application_sdk/ had 126 over-limit functions when they were enabled (FND-4266). Each is named, by file, rule and qualified name (Class.method), in .github/scripts/complexity_baseline.json, and .github/scripts/check_complexity_baseline.py holds the tree to it:

    • A function not in the baseline fails. It is new, or grew past a limit. Split it. The failure prints the ruff finding for each one.
    • A baseline function no longer over a limit also fails. Lock the improvement in with --update. --update refuses to add a function unless given --allow-increase, and the base check below still catches that.
    • A baseline entry the base revision lacks fails. The CI script tests job passes --base-sha. An entry matches the base's in the same file. A module split that moves an over-limit function unchanged passes: a base entry carries to another file only when its own file no longer defines a function of that name and the function's AST (formatting and comments aside) is identical at base and in the new file. A same-named replacement, a function edited while it moves, or a renamed one counts as new: move it unchanged and change it in a later PR. A base with no baseline file is measured on its own tree.
    uv run --frozen python .github/scripts/check_complexity_baseline.py           # check
uv run --frozen python .github/scripts/check_complexity_baseline.py --update  # lock in a reduction

    Naming functions rather than counting them per file means paying one function down cannot buy room for a new one in the same file.

    The baseline is the only suppression. As with ANN401, ruff runs with --isolated and --ignore-noqa, so no select, ignore, per-file-ignores, exclude, nested ruff.toml, raised max-complexity / max-statements or # noqa: C901 can hide a function. The thresholds (ruff's defaults) and the target version are passed on the command line. A tree with nothing left passes when ruff still flags a canary over both limits.

    The complexity-baseline pre-commit hook runs the check on every change under application_sdk/. packages/conformance has its own count-based baseline for the same rules (above).

    Artifacts move through the retry composites

    actions/upload-artifact treats the artifact service's FinalizeArtifact 403 as non-retryable and fails the step, and actions/download-artifact does the same with a ListArtifacts 403. So every upload and download goes through one of two composites that hold the retry:

    - name: Upload test results
  if: always()
  continue-on-error: true        # only when a lost artifact must not fail the job
  uses: atlanhq/application-sdk/.github/actions/upload-artifact-retry@main
  with:
    name: integration-test-results
    path: results/
    retention-days: 14

- name: Download test results
  uses: atlanhq/application-sdk/.github/actions/download-artifact-retry@main
  with:
    pattern: integration-test-results*
    path: results/

    Each composite runs a first attempt with continue-on-error: true, a 20-second wait and a retry, both guarded on the first attempt's outcome. The step fails only when both attempts fail. The caller's if: gates the whole thing. A workflow that only ever runs in this repo, on a checkout of it, may use the relative ./.github/actions/... ref (codeql.yaml does, so a PR exercises its own version of the upload composite); reusable workflows and composites must use atlanhq/...@main, because a relative ref resolves against a consumer's workspace.

    conformance-reusable.yaml still writes its 12 SARIF pairs by hand: this repo's own PR CI runs it, and an @main ref to a composite that is not yet on main fails the job at setup. It moves in a follow-up once the composites merge.

    The upload composite follows these rules:

    1. The retry uploads under <first attempt's name>-retry. A failed finalize leaves an artifact record that holds the name for the rest of the run but never becomes visible: it is absent from GET /actions/runs/<id>/artifacts, and overwrite: true deletes by looking the name up in that same listing — so it finds nothing, skips (on a core.debug line, invisible in the log), and CreateArtifact then 409s on the record it could not see:
    Upload test results          FinalizeArtifact -> (403) Forbidden   [warning]
Upload test results (retry)  CreateArtifact   -> (409) Conflict:
                             an artifact with this name already exists

    A same-named retry can therefore never absorb the one failure it exists for, and on a fatal path it turns a warning into a red job after all the expensive work has passed. overwrite: true stays on the retry for the case it does handle: re-running a failed job inside a run that already holds the artifact.

    1. A backoff step sits between the two attempts (run: sleep 20, guarded on the same outcome). The 403 comes from an intermediary having a moment; an immediate retry lands in the same window and both attempts fail together.

    2. Both attempts set overwrite: true — the first attempt is the load-bearing one. Artifacts survive across attempts of a run, so without it re-running a failed job 409s on the first attempt, hands the upload to the retry, and leaves both <name> (from the earlier attempt) and <name>-retry live. A merge-multiple consumer then flattens two files of the same inner name in undefined order — for trivy-results that means the Security Gate judging the previous attempt's scan. Overwrite is what keeps at most one live artifact per name, which is the invariant the globs below rest on.

    3. Consumers accept the retry name. Three shapes, pick per call site:

    4. same-run download-artifact: pattern: <name>* + merge-multiple: true, never an exact name:;
    5. cross-run gh run download: resolve the name from the run's artifact listing first (newest live match of <name> or <name>-retry) and pass that — a hard-coded --name <name> silently no-ops on a retried upload;
    6. a jq/regex selector: match either name explicitly.

    Note that with pattern: (unlike name:) download-artifact treats "nothing matched" as success, so any step gated on steps.<download>.outcome has to move onto hashFiles(...).

    .github/scripts/tests/test_artifact_upload_retry.py and test_artifact_download_retry.py pin these rules on the composites, fail on any direct actions/upload-artifact or actions/download-artifact step elsewhere, and check that no consumer addresses a retried artifact by its base name alone. EXEMPT in each carries the reason for a direct call that needs no retry.

    Test legs are requested by PR comment, never by label

    Rule: no test workflow subscribes to labeled or unlabeled. The expensive legs are requested with a PR comment, and the result is a commit status on the head commit:

    Comment Where What runs Verdict
    /e2e any PR the live-tenant e2e suite on the head commit e2e status
    /gate-check bump-version* PRs the PR's full release gate (FND-3748) gate-check status
    … force either the same, even though the commit already passed

    Only commenters with the Write, Maintain or Admin role on the repo count (read live from the collaborator-permission API: the comment's author_association is a relationship, not a role — MEMBER is any org member, even one with only Read). In application-sdk, /gate-check needs the Admin role: it gates an SDK release (--gate-check-requires-admin in test-commands.yml); bots and fork PRs are refused. The decision is in pr_test_command.py, wired by test-commands.yml here and by the scaffolded test-commands.yaml (calling test-commands-reusable.yaml) in connector repos (FND-3839).

    Why not labels: a label add is a pull_request labeled event, and GitHub has no trigger-level filter for which label. So every label any bot added started another run of every subscribed workflow on the same commit. That second run's unit job shared the first's cancel-in-progress group, cancelled it, and the cancelled run's Tests Gate concluded FAILURE. GitHub resolves a required check to the newest run, which is luck, so PRs sat BLOCKED with a green run underneath (FND-48, FND-2167, FND-3832). The job-level label filter that FND-48 added stopped the jobs, never the runs. A comment creates no pull_request event, so one push is one run.

    How the three properties hold:

    • Repeatable. A request is bound to the head commit when it was made, and so is the verdict. A push makes a new commit with no status, so nothing has to "consume" the request. A dispatched run whose branch moved before it started stands down instead of testing a different commit (head_sha), and one whose branch moves before the tenant lease stands down there (e2e_branch_recheck.py).
    • No tangle. The comment never starts a second run of the PR's own workflow. In connector repos it dispatches tests.yaml with run_e2e: only, whose caller job is named e2e, so its checks are e2e / …. That naming is load-bearing: GitHub resolves a required check to the newest run on the commit and counts a skipped job as a pass, so an e2e-only run publishing a skipped tests / Unit would override a real unit failure. The command refuses a branch whose tests.yaml predates the naming. In application-sdk, whose PR workflows cannot be dispatched without the same collision, the comment posts a marker status (e2e-request, gate-check) and re-runs the runs on the commit that started before it; they read the marker live.
    • Cost. A commit whose verdict is already success is not run again, and a request while one is in flight is refused; the command workflow is serialised per PR so two comments cannot both pass that check. An e2e-only run skips the unit and integration tiers its PR run already measured.

    What the PR shows. One sticky comment per command (/e2e, /gate-check), found by a hidden <!-- test-commands:<command> --> marker and edited in place through the request — requested, running, then the verdict with an expandable suite × cloud (or per-workflow) table. It shows the latest request only. Reactions answer the comment at once: 👀 seen, 🚀 started, 👍 nothing to do (already passed or running), 😕 refused; a refusal for a reason (behind the base, an old tests.yaml) shows in the sticky, an unauthorised one gets a short reply. The comment is a view, never state: the commit status is the verdict gates read, so a failed or deleted comment changes nothing (test_command_comment.py).

    Gates read the status, and are re-run when it lands. The PR run's Tests Gate holds to the e2e status (e2e_commit_verdict.py). A dispatched e2e run re-runs that gate job when it disagrees with the verdict (rerun_deferred_gate.py --verdict). A /gate-check resolves when the last dispatched run finishes: gate_check_verdict.py, on workflow_run, sets gate-check to success only if all of them passed and re-runs Release Gate, which passes only on that success.

    A dispatched run never satisfies a PR's required checks. GitHub counts only the PR's own pull_request runs toward them. So on a bump PR the connector shims run their reusable anyway, with skip-on-bump-pr: true, which skips every job in it. The skipped jobs file each required <caller> / <job> check as skipped at no cost, and Release Gate is the one blocker (FND-3947; see release-flow.md). Skipping the caller job instead files no required name at all, so the PR waits at "Expected" forever.

    Concurrency. Pushes are handled by the existing per-ref groups on the unit and integration jobs: a new commit cancels the old commit's run, and since there is one run per commit, a cancel can only land on a commit that is no longer the head. E2e legs keep cancel-in-progress: false (an abandoned Automation Engine run has no tenant cleanup, FND-252); a superseded commit's run stands down at the lease instead.

    Legacy callers. Connector repos not yet resynced still subscribe to labeled, so tests-reusable.yaml keeps its label gates behind e2e-label-trigger (default true; the current scaffold passes false), and those gates must still check which label fired:

    contains(github.event.pull_request.labels.*.name, 'e2e') &&
(github.event.action != 'labeled' || github.event.label.name == 'e2e')

    test_label_trigger_gates.py enforces that term and fails any workflow or scaffold that subscribes to labeled. Both the gates and the input go once the fleet has resynced.

    Review is requested by comment too, in a workflow of its own. In connector repos /review asks the connector reviewer for an AI review of the pull request, judged against application-sdk's fleet principles and the repository's own (.github/connector-reviewer/principles/ in each). It is not a test command: the scaffolded connector-reviewer.yaml handles it, calling connector-reviewer-reusable.yaml, on issue_comment and workflow_dispatch only. The result is one summary comment and a connector-reviewer status on the head commit. Unlike test-commands.yaml it has no concurrency: group: the reviewer holds its own lock, found by the run name, so a running review finishes and a second request is dropped. It replaces the review gate that ran on every pull request and review event (connector-review-gate.yaml, retired in FND-5317; bootstrap removes it and its script, and C002 reports a copy still on disk).

    Release Gate requires that status (FND-5321). A pull request merges only when the reviewer App's newest connector-reviewer status on its head is success: every finding fixed or dismissed, /review waive for that head, or /review answering exempt. pending reads "still running", error "re-run /review", failure names the open findings (the gate's job summary lists each one's id, severity, title, principle and suggestion, read from the reviewer's own summary comment), and no status reads "comment /review". A pull request the reviewer would not review passes without one, decided by the reviewer's own classifier (connector_reviewer.review.exemption with config.toml's [exempt] lists), and only while the reviewer has never reviewed it. A push moves the head to a commit with no status, so the gate blocks again. The reviewer posts its status with its App token, which fires a status event; release-gate.yaml's rerun-on-review job (default branch, actions: write, skipped for every other context) re-runs the newest Release Gate run on that commit through gate_check_verdict.rerun_release_gate, the same re-run a gate-check verdict uses. The decision is .github/scripts/release_gate.py in this repository, checked out at main by the shim; bootstrap no longer vendors it. The gate job runs on pull_request, as it always has, so no org or repository Actions policy is needed. Nothing of the pull request is checked out or run: the pin check reads uv.lock and pyproject.toml at the head through the API, and a pull request that edits the old vendored script changes nothing. The exposure that every pull_request gate already had remains: a pull request can edit release-gate.yaml itself, or add its own job named Release Gate. Such an edit is in the diff, and the connector reviewer's gate-file check raises a high finding on any hand edit to a bootstrap-managed workflow (FND-5325).

    The gate posts no PR comment. Why it failed and what to do ("comment /review", the open findings, "still running", "re-run /review", the /gate-check reason on a release PR) is in the Release Gate check: its error annotation and its job summary. python release_gate.py explain --repo <owner/name> --pr <n> --config-dir .github/connector-reviewer prints, read-only, what the gate and the reviewer's classifier decide for any real pull request.

    Bot-opened PRs are never labelled

    Rule: a lane that opens PRs from a bot (the conformance resync lane, conformance_resync.py) must not add labels to them, on open or on any later update. Identify lane PRs by head branch + author — for the resync lane, bot/conformance-resync + atlan-conformance-sync[bot] — which is what every consumer (the resync approval gate, the Renovate auto-approve routing, Connector Pulse) already matches on.

    Why: every label add is a labeled event, and connector tests.yaml files not yet resynced past FND-3839 still subscribe to it (see above). Labelling a PR a second after opening it starts a second Tests run on the same head SHA there; the unit job's cancel-in-progress concurrency group lets that run cancel the first one's unit job, and the cancelled run's Tests Gate concludes FAILURE. GitHub counts every run of a required context, so the PR stays BLOCKED and auto-merge never enqueues it, even though the second run is green. FND-3832 found this on most open resync PRs.

    If a human-readable cue is wanted, put it in the PR title (resync PRs already start with chore(conformance): resync).

    The same rule covers Renovate: the fleet preset applies no labels (FND-2201), and classifies its PRs by branch slug instead.

    Enforced by test_no_bot_pr_labels.py, which sweeps .github/, renovate-config/ and the conformance bootstrap templates for every way code adds a PR label, and parses each Renovate config for labels / addLabels / :label presets. Sites that predate it are grandfathered by exact count, each with its reason. A new site fails, and so does a removed one until its count is updated.

    CI cost

    Cost is part of authoring a workflow, not an afterthought. Review it at the diff, before a pattern is copied into every connector.

    Billing model

    • Each job is rounded up to a whole minute. A 9-second job bills 60 seconds, and so does a job that starts and then skips every step.
    • Larger runners and macOS cost a multiple of standard Linux. Pick the runner from measured need (see "Runner sizing" below).
    • Artifact storage is billed per GB-day for as long as the artifact is kept, not once at upload.
    • Standard runners are free on public repos, so application-sdk's own workflows cost nothing to run. The bill comes from private connector repos running the reusables and bootstrap templates this repo ships.

    Levers, in priority order

    1. Number of billed jobs. Every job carries the one-minute floor, so job count dominates for short work. Collapse fan-out before tuning steps.
    2. Churn: how many times the workflow fires. Superseded runs left running, rebases, workflow_run fan-out and crons multiply everything else.
    3. Duplicate work across PR, merge queue and release. A check whose inputs are unchanged since it last passed repeats a verdict and bills for it (see "What a merge-queue entry re-runs" below).
    4. Run length and runner size. Matters only once the three above are right.

    Rules

    • Filter at job level, not step level. A job skipped by its if: is not billed. See "Skip whole jobs, not steps" below.
    • No matrix for sub-minute work. Each matrix leg is its own billed job, so a matrix of N 10-second legs bills N minutes. Loop inside one job instead.
    • Every PR-triggered workflow cancels superseded runs. Declare a concurrency: group keyed on the PR ref with cancel-in-progress: true on PR refs (the pattern is in "concurrency: is not a lock, and not a queue" below). A workflow that must not cancel, such as one holding a tenant, says why in a comment beside its concurrency: block.
    • Every upload-artifact sets retention-days. Without it the artifact keeps the repository's retention setting (90 days unless changed), far longer than any CI consumer needs. Pick the shortest window that covers the artifact's real readers.
    • Every new workflow_run trigger counts its fan-in. It fires once for each completed run of each workflow it names, on every branch unless branches: narrows it. The PR description states how many runs that is per PR.
    • Every new cron justifies its frequency. A schedule bills on every repo that carries it, whether or not anything changed. State in a comment why the interval cannot be longer.

    Fleet multiplier

    Anything in a bootstrap template or a reusable workflow runs in roughly 140 repos. One extra billed minute per PR there is ~140 minutes per fleet-wide PR cycle, and a cron that fires hourly is ~3,360 jobs a day. Judge a template or reusable change by its fleet total, not by the single run you watched.

    Weekly cost report

    actions-cost-report.yaml runs every Monday. It scans a seeded sample of 12 fleet repos with actions_minutes_report.py over the last two complete weeks and compares them in actions_cost_weekly.py. It publishes the top workflows and jobs with week-over-week deltas to the run summary and to Kryptonite (actions-cost-dashboard/, history keyed by week). It posts to Slack (SLACK_ACTIONS_COST_WEBHOOK) when the sample's total billed minutes, or any one workflow with at least 300 billed minutes this week, grew more than 25%. A workflow that is new this week counts as growth. If there is a regression and the alert cannot be delivered, the run fails.

    A cost change you expect, such as a new required job, will still alert once. Say so in the PR so whoever reads the alert can match it to the change.

    Handing a hotspot to the repo that owns it

    Much of the bill comes from repos this team does not own. For those, we measure the cost and hand it over; the owning team makes the fix. A handoff includes:

    1. This section. The billing model, levers and rules above apply to any repo, not just the fleet.
    2. That repo's own per-workflow report. actions_minutes_report.py takes --repo in place of fleet discovery. Run two comparable weeks so the owner can see what changed:
    GH_TOKEN=... python3 .github/scripts/actions_minutes_report.py \
    --repo atlanhq/<repo> --since <monday> --until <sunday> --out-dir /tmp/<repo>-<week>

    For each workflow, compare runs against billed minutes. If runs went up, the trigger fires more often (lever 2). If billed minutes per run went up at the same run count, the job is running longer (lever 4). 3. The report's blind spot. It counts minutes on the standard-Linux rate, because check runs carry no runner labels. If a repo uses larger runners or macOS, its minutes cost a multiple of the figure shown. Before you rank that repo against others, read the labels on its jobs from the REST /actions/runs/{id}/jobs endpoint. 4. Whether the cost comes from us. Check whether the repo calls a reusable from this repo (uses: atlanhq/application-sdk/...) or is triggered by a fleet event (workflow_run, repository_dispatch). If so, the fix may be ours, not theirs. Minutes from a cross-repo dispatch bill to the repo that runs the job, not the repo that sent it.

    Track each handoff and its outcome in Linear, not in this repo.

    Review checklist

    For any change under .github/workflows/, a reusable, or a bootstrap template:

    • [ ] Does the change add billed jobs? Could the work run as steps in an existing job instead?
    • [ ] Is every "nothing to do" filter on the job's if:, not on its steps or an early exit?
    • [ ] Is there a matrix whose legs finish in under a minute?
    • [ ] Does each PR-triggered workflow cancel superseded runs, or explain why not?
    • [ ] Does every upload-artifact set retention-days?
    • [ ] Does a new workflow_run trigger state its fan-in? Does a new cron state why its frequency is needed?
    • [ ] Does the same check now run on PR, merge queue and release with unchanged inputs?
    • [ ] For a template or reusable: what is the cost multiplied by ~140?

    Skip whole jobs, not steps

    Rule: when a job has nothing to do on some event, actor or branch, put the filter on the job's if:, not on each of its steps or as an early exit in its script.

    Why: a job skipped by its own if: is not billed. A job that starts and then skips every step, or runs a script that passes at once, is billed a full runner minute. In a reusable that every connector calls, that minute is paid on every PR, push and merge-group run across the fleet (FND-3320: renovate-artifacts in tests-reusable.yaml, and the merge-group no-ops in commits.yaml and release-gate.yaml).

    It is safe for a required check as long as the job name: is a static string. A job-level skip still files its check run, with conclusion skipped, and GitHub counts skipped as a pass for a required context (see "A skipped job is not a silent job" below for the same-commit trap). What leaves a required context pending forever is no check run at all, which happens when the caller never dispatches on the event (no merge_group: trigger) or when the job name is an expression that renders differently on the skipping event. When a downstream gate reads the skipped job's needs.<job>.result, make it accept skipped explicitly.

    A path filter lists what a test reads, not only where it lives

    Rule: when a test reads a file from another area of the repo, put that file in the sdk-gate.yaml path filter that runs the test's job.

    Why: a drift guard runs only when its job's filter matches. If the filter lists the guard's own directory but not the file it reads, a PR that edits only that file merges without the guard. The drift then shows up on a later, unrelated PR. FND-4907 found three cases:

    • the canonical .github/ sources of the bootstrap templates, checked by packages/conformance/tests/test_bootstrap.py (now in conformance_pkg);
    • toolkit examples read by SDK and conformance tests (now in sdk and conformance_pkg);
    • application_sdk modules the generated toolkit examples import, checked by contract-toolkit/scripts/test-sdk-import.py (now in toolkit).

    Enforced by .github/scripts/tests/test_sdk_gate_filter_coverage.py. It finds these reads in the source, so a new one fails until its filter covers it. A drift guard whose input is missing fails; it does not skip. A skip turns the guard off without anyone noticing.

    What a merge-queue entry re-runs

    Rule: on merge_group, a check runs only if its result can change when the PR is combined with the latest base. Every other check skips at job level, as above, and its skipped check run passes the required context.

    Why: the queue exists to catch what the combination changes. A PR cannot enter the queue until its required checks are green on its head, so a check whose inputs are identical on the queue commit can only repeat that verdict, and every repeat bills a runner across the fleet (FND-3321).

    Six bootstrap callers declare merge_group:. Each check is either base-sensitive or not:

    Caller → job Base-sensitive? On a queue entry Why
    commits.yaml → Conventional Commits No Skipped (FND-3320) The PR title and commit messages do not change when the PR is combined with the base.
    release-gate.yaml → Release Gate No Skipped (FND-3320) It reads the head commit's gate-check status (FND-3839) and connector-reviewer status (FND-5321). A pull request without the verdicts it needs fails on the PR and never enters the queue.
    tests.yaml → unit, integration Yes Skipped when the queue tree equals the PR head tree, the head already contains the queue's base, and github-actions[bot]'s newest gate-check status on that head is success (FND-4344). Otherwise always runs Behaviour of the merged code. Integration is skipped on the PR when a queue is detected, so the queue run is the one that gates, except on a release PR: /gate-check already ran the whole suite on the head commit, and refuses a head that is behind its base.
    conformance.yaml → Conformance Gate Only through the tree Skipped when the queue tree equals the PR head tree and the head already contains the queue's base The suite reads only the tree.
    checks.yml → Pre-commit Only through the tree Skipped when the queue tree equals the PR head tree and the head already contains the queue's base Lint and type checks read only the tree. A base change can break them (a renamed symbol), so a different tree re-runs them.
    vulnerability-scan.yml → Build Image, Security Gate Only through image inputs In a repo with a release flow: always skipped (FND-3328, see below). Otherwise: skipped unless an image input may differ from what the PR tested Findings come from the image's packages: base image, Dockerfile, dependency locks and manifests, vendored binaries, install scripts. The caller's .security/ allowlist changes the verdict too. Python source never adds a finding.

    The last three share a decision job, queue-diff, a ubuntu-slim job that runs .github/scripts/queue_tree_diff.py only on merge_group. Its body is one nested reusable, queue-diff-reusable.yaml, which each of the three reusables calls with ./ (FND-4928); each keeps its own if:. It reads the PR number from the queue branch name (gh-readonly-queue/<base>/pr-<N>-<sha>) and fetches the PR head from refs/pull/<N>/head. The SHA in the branch name is the commit the entry was built on, the queue commit's parent, not the PR head. Until FND-4344 the script read it as the head, so identical was never true and these skips never fired. It takes the queue's base from merge_group.base_sha, fetches the commits and trees (no blobs, bounded depth) behind both, and compares them with the queue commit. It writes three outputs: identical (the whole tree matches and the head already contains the base), image_changed (a path in the script's image-input list may differ) and pr_head (the head it compared against). Every git call has a timeout, and a timeout runs every check. The skipping job's gate is !cancelled() && needs.queue-diff.outputs.<x> != '<skip value>', so an empty output still runs the check. That covers a skipped queue-diff on every non-queue event and a failed one. test_queue_entry_rechecks.py evaluates each gate in both directions.

    What "may differ" means. The PR's run built refs/pull/N/merge: the head merged with the base as it was then, a base commit the queue cannot know. The head-to-queue diff alone misses one case: a base change that was there when the PR ran and was reverted before the queue entry. The queue tree then equals the head's but not the tree that was tested. So the paths that may differ are the head-to-queue diff plus every path a base commit touched since the PR forked (git log fork..base), reverted or not. When the head already contains the base, that second set is empty and the tested tree was the head's own: the only case in which identical can be true. A fork point beyond the fetched depth runs every check. When a group batches several PRs, the queue branch names the last one. The PRs ahead of it then show up as a difference, and the checks run.

    No separate queue-gate reporter. A job-level skip with a static name: already files the check run the required context waits for. A reporter job that posts the contexts itself would need checks: write in every caller, and it would have to keep its context strings in sync with the job names by hand.

    Newest suite wins, and that is safe here. A queue commit belongs to one entry. Nothing else runs on its SHA, so no later skipped run can override a real failure. That differs from the same-commit labeled trap below. A requeue after an ejection builds a new queue commit. The skip adds no concurrency: group either, so it adds nothing to the FND-218 eviction surface.

    What it does not cover:

    • A floating base-image tag (FROM …:latest) can move without any file changing, and so can the vulnerability DB. Both drift the same way between any two scans, queue or no queue. build-and-publish-app.yaml scans the image it pushes: blocking on an SDR deploy-on-merge push to main and on a release that had to rebuild, report-only on a release that promoted the scanned bump-PR candidate. Non-SDR apps build no image on a merge (FND-3327).
    • A Dockerfile under a name the image-input list does not match (the list is by basename: Dockerfile*, *.dockerfile, Containerfile). atlan.yaml, which names the Dockerfile, is on the list. A bespoke name still needs adding there.
    • Unit tests, outside a release PR. They are base-sensitive and could skip on an identical tree too, but on an ordinary PR the integration tier they feed Tests Gate with has not run anywhere else, so the queue run is still the first one. A release PR's queue-proof job (tests-reusable.yaml) skips both, together with Tests Gate, because /gate-check ran them on the head commit. It runs the same queue_tree_diff.py, then queue_gate_check_proof.py reads the head's gate-check status, trusting only github-actions[bot] as Release Gate does.

    The SDK's own integration tier runs in the queue only (FND-4306)

    application-sdk follows the connector split. In sdk-tests-reusable.yaml, Integration Tests and Storage Emulator Tests run on merge_group and on v* tag pushes, and on a PR only when someone asks for the full suite. Unit legs and Unit Perf Tests still run on every PR push.

    On demand. A /e2e or /gate-check comment runs the integration tier on that PR commit too. The reusable's Decide integration request job reads the e2e-request and gate-check statuses live (bump_pr_opt_in.py integration-requested), and only the two tier jobs need it. /e2e re-runs that one job (pr_test_command.py, SDK_E2E_RERUN_JOBS): GitHub re-runs it, the tier and SDK Gate's verdict, and keeps the unit legs' result from the first attempt, so /e2e never runs or cancels the unit legs. /gate-check re-runs the whole run, as before. A status that cannot be read runs the tier: that costs runner minutes, never a lost request. A new push is a new commit with no marker, so the tier skips on it again.

    On a PR without a request the skipped jobs report skipped, SDK Tests concludes success, and SDK Gate reads that as a pass, so the required check still concludes on the PR. Every queue entry that touches SDK code escalates to the full suite (sdk-gate.yaml, "Synthesize final force flags"), so nothing lands on main without integration passing.

    Measured before the change (2026-10-13 → 2026-10-21, 1000 SDK Gate runs): PRs averaged 5.8 pushes, and integration ran 8.9 minutes p50 on each, about 50 runner-minutes per PR. Over the same window, three PR-side integration failures came from one PR, and no queue failure was an integration break the PR run had missed. The cost of the move is about one extra queue ejection in that window.

    The SDK's unit grid is reduced on PR pushes (FND-4673)

    The unit job in sdk-tests-reusable.yaml is an OS × Python grid: 3.11–3.14 on ubuntu-22.04, macOS-latest and windows-latest, 12 legs. An ordinary PR push runs 6 of them: all four Pythons on Linux, and only the container's Python (the Dockerfile's golden tag) on macOS and Windows. The merge queue, v* tags, and release/* and bump-version-main PRs (force_sdk) run all 12. sdk-gate.yaml decides this and passes it as the reusable's full-unit-grid input, which defaults to true so a caller that omits it keeps the full grid.

    The trade: a break that shows only on macOS or Windows and only on 3.11/3.12/3.14 fails in the queue, not on the PR, and costs one ejection. Before the change every PR push ran 12 unit legs, with Windows the critical path at p50 447 s, and PRs averaged 5.8 pushes.

    test_container_python_version.py expands the exclude: expression the way GitHub does and fails if the PR grid stops being "all of Linux plus the container's Python elsewhere", or drops the coverage leg. Bumping the Dockerfile's Python therefore fails that test until the exclude list moves with it.

    with-retry.sh's tests are pytest (test_with_retry.py) and run in pytest .github/scripts/tests; there is no bats job or bats-core checkout.

    The vulnerability scan gates the bump PR, not every PR (FND-3328)

    Since FND-3327 the only image a release-flow app ships is the release image, so a scan per PR checked an image that never shipped. In a repo whose base branch has a job calling release-version-bump.yaml (a job-level uses:; a comment or string naming the file does not count, since a false match turns scans off), build-and-scan.yaml now scans only the bump-version* PR. Its scope job (.github/scripts/vuln_scan_scope.py) answers scan=false for every other PR and every queue entry, and Build Image / Security Gate skip on that answer. A skipped job files its required context as passing, which is why the skip is inside the reusable workflow: dropping the caller's triggers would file no context at all and block every PR. Security signed off on this posture.

    Repos with no release flow scan every PR and queue entry as before: without a bump PR nothing else would gate their image. A caller can also opt back in with scan_every_pr: true. The release-flow check reads the base branch, so a PR cannot opt itself out, and an unreadable base reads as "no release flow", i.e. scan.

    The bump PR scans the image the release ships. The template's candidate job runs build-and-publish-app.yaml with candidate: true on the PR's merge commit, pushing the full release build as :candidate-<tree> (<tree> is the git tree SHA). The scan scans that digest, blocking, and on a pass tags it :scanned-<tree>. At release, prepare looks up :scanned-<tree> for the tree being released and merge copies that manifest to every release tag with no build; the copy reads each tag back and fails unless the digest matches. The tree, not the commit, is the key because the squash-merge commit is never a commit the PR built. When the base moved before the merge the trees differ, nothing is promoted, and the release rebuilds behind a blocking scan. Mechanics: .github/scripts/release_candidate.py; release-side detail in release-flow.md.

    The Renovate lock refusal moved with it. A refused lock bump is withheld by a lock carrying an undeclared [options] table (renovate_uv_lock_bounded.py, withhold). The image build's uv sync --locked behind the required scan / Build Image used to reject it. That job now skips on ordinary PRs, so two shared workflows run uv lock --check (.github/scripts/check_uv_lock.py) whenever uv.lock or any pyproject.toml differs from the base (a dependency added without relocking leaves the lock unchanged): the Pre-commit job of checks-reusable.yaml, and the Conformance Gate job of conformance-reusable.yaml. The second is the one that holds fleet-wide: suite / Conformance Gate is required in every repo, while some repos require no pre-commit / Pre-commit context or never call checks-reusable.yaml. Both sit in shared workflows, not bootstrap templates, so they go live in the same merge as the skip.

    Every unit leg runs a socket guard

    Rule: every SDK unit leg, Windows included, runs pytest-socket with --disable-socket --allow-unix-socket. .github/scripts/unit_test_command.py builds the flags, and its tests pin them.

    How Windows survives it: ProactorEventLoop's self-pipe is socket.socketpair(), and Windows has no native one. CPython emulates it with two AF_INET sockets on loopback, created through the guarded socket.socket, so every new event loop would fail. On Windows, tests/conftest.py replaces socket.socketpair with tests/socket_guard.py's loopback_socketpair. That function builds the same pair from the socket class captured at collection, before pytest-socket swaps it. Every socket a test creates itself is still refused. tests/unit/test_socket_guard.py proves this on every OS.

    Not --allow-hosts: it patches socket.connect() only. On Windows, asyncio connects through ConnectEx, and UDP sends through sendto. Neither calls connect(), so a host allowlist guards neither.

    Dapr, locally too: a plain local pytest run has no socket guard. The autouse _intercept_dapr_sidecar fixture in tests/unit/conftest.py gives application_sdk.infrastructure._dapr.http a private httpx whose transport raises UnmockedDaprSidecarCallError, so a test that forgot to mock Dapr fails the same way everywhere. A test that wants a Dapr answer mocks the client or swaps the transport. If the module stops importing httpx, the fixture raises at setup, so a refactor cannot leave the interceptor silently patching nothing. That happened to the DaprClient mock it replaced (FND-4287).

    Runner sizing

    Rule: a short glue job (it calls the GitHub API, rolls up results, posts a comment or uploads a file) runs on ubuntu-slim. Everything else stays on ubuntu-latest until it has a measured reason to move.

    Why: every job is billed in whole minutes, so a 9-second job costs the same 60 seconds as a 59-second one. ubuntu-slim (1 vCPU) is billed at $0.002/min against ubuntu-latest's $0.006/min, so a sub-minute job costs a third as much there. This only matters for jobs that run in private repos: standard runners are free on public ones. application-sdk is public, so its own workflows save nothing by moving. The saving comes from the reusables and bootstrap templates that private connector repos run (FND-3335).

    What ubuntu-slim provides

    Checked on 2026-10-06 against GitHub's hosted-runner reference and the runner-images ubuntu-slim README and Dockerfile (image 20260925). Check them again before relying on anything not listed here.

    • 1 vCPU, 5 GB RAM, 14 GB disk, x64, Ubuntu 24.04.
    • A hard 15-minute job timeout. A longer timeout-minutes is ignored. The job is killed and fails.
    • An unprivileged container, not a VM: no Docker daemon. That rules out services:, container:, Docker actions, and docker build/run/pull. The Docker CLI is installed but has nothing to talk to.

Not installed: uv (use astral-sh/setup-uv), pkl, trivy, and the apt Python modules the full image's system interpreter has (PyYAML, packaging). A script run with the system python3 must import the stdlib only.
    • sudo is present, but nothing here has verified it inside the unprivileged container. Jobs that sudo/apt-get stay on ubuntu-latest until a canary confirms it, and that includes install-pkl, which does sudo mv.

    .github/scripts/tests/test_runner_sizing.py enforces all of this for every runs-on: ubuntu-slim job: a declared timeout of 15 or less, no Docker, no root, only allowlisted actions (each checked to be node24 at its pinned SHA), and stdlib-only system Python. To move a job, add it and let that test tell you what it needs.

    Mask secrets before writing them to $GITHUB_ENV

    Rule: if a step derives secret values from something else — unpacking a composed blob, decoding a bundle, reading a credentials file — it must register each derived value with ::add-mask:: before the value reaches $GITHUB_ENV, $GITHUB_OUTPUT, or anything a later step prints.

    Why: the runner's log masker replaces occurrences of each registered string. It does not match substrings of one. Registering a composed blob (toJSON(...) of several secrets, say) therefore redacts the blob and nothing inside it, so the first later step that renders its env: group prints each extracted value in cleartext. secrets: inherit does not help: inheritance controls which secrets a job can read, not which strings the masker knows.

    The stdout constraint: ::add-mask:: is a workflow command the runner reads from the step's stdout. A script whose stdout is redirected into $GITHUB_ENV cannot emit mask commands on that stream — they would be written into the env file as garbage. Do not fall back to stderr; workflow commands on stderr are not a documented guarantee. Split the two outputs into two modes and call the masking one first, so a failure aborts the step before anything is written:

    - name: Export caller-supplied credentials
  run: |
    set -euo pipefail
    python3 .github/scripts/<driver>.py --json "$PAYLOAD" --mask-only
    python3 .github/scripts/<driver>.py --json "$PAYLOAD" >> "$GITHUB_ENV"

    Set -e explicitly rather than relying on the runner's default shell: a workflow- or job-level defaults: run: shell: added later drops the implicit -e, and the step would then fail open — the mask pass errors, the env write still runs, and the values land unregistered. Composite actions declaring shell: bash are immune (they ignore workflow defaults), but it costs one line to make the property local to the step.

    Mask every scalar, not the ones that look sensitive — the caller decides what goes into the payload, so a driver that guesses will guess wrong. Skip empty and whitespace-only values (the runner refuses those with a warning). Multi-line values need each line registered as well as the whole value: the masker is handed log output a line at a time, so a registration spanning newlines matches nothing. Never put a value in an error message.

    What masking does not cover: ::add-mask:: rewrites the log stream the runner uploads. It does not touch bytes on disk. A step that tees output into a file — results/, a JUnit XML, a container log — writes the value unredacted, and upload-artifact then ships it to anyone with repo read access for the retention window. Masking is not a substitute for not writing the secret: anything destined for an artifact has to be scrubbed at the source that produces it, or kept out of that file in the first place.

    export_extra_env.py and test_export_extra_env.py are the worked example, including a static check that every call site masks before it writes.

    Never pass a credential as a Docker build-arg

    Rule: a step that builds an image must not put a token, password, or key in build-args:. Feed it through secrets: instead, and have the Dockerfile read it with RUN --mount=type=secret.

    # WRONG — publishes the credential with the image
build-args: |
  ACCESS_TOKEN_PWD=${{ secrets.ORG_PAT_GITHUB }}

# RIGHT — the value is available during the RUN and nowhere after it
secrets: |
  git_token=${{ steps.image-git-token.outputs.token }}

    The token itself is a read-only fleet App token minted in the same job, scoped to the private atlanhq repositories the app names as git dependencies (the mint steps below), never ORG_PAT_GITHUB. When the app names none, nothing is minted and no secret is passed. A secret mount keeps the token out of the image, but not out of the RUN: every build backend that uv sync runs can read it, which is why it is scoped to what the build needs. test_image_build_git_token.py pins this.

    RUN --mount=type=secret,id=git_token,uid=1000 \
    UV_GIT_TOKEN="$(cat /run/secrets/git_token)" \
    uv sync --frozen --no-dev

    Why: a build arg is not a build-time-only variable. BuildKit records the ARG name and its value in the image config, so docker history <image> prints it back to anyone who can pull the image — no repo access, no Actions log access, no runner access needed. The credential is published as part of the artifact, and it stays published in every tag ever built that way; deleting the workflow line does not retract the images. ::add-mask:: does not help here for the same reason it does not help with artifacts: it rewrites the log stream, not bytes written elsewhere.

    A --mount=type=secret is exposed as a tmpfs file for the duration of one RUN and is not part of that layer, the image config, or the history. It is also the only form that survives layer caching correctly: a build arg changes the cache key, so rotating the credential invalidates every layer after the ARG.

    Migrating a consumer: build-args and secrets are not interchangeable at the Dockerfile end, so the two sides have to move together. Land the Dockerfile change first — a Dockerfile that mounts git_token ignores an ACCESS_TOKEN_PWD build arg it no longer reads, so it builds green under both the old and the new workflow — then drop the build arg from the workflow. Doing it the other way round leaves the build with an empty credential, and uv sync against a private git dependency fails on the next build rather than at merge.

    Scope note: this covers credentials only. Non-secret build inputs — a version string, a target arch, a base-image reference — are what build-args are for, and recording those in image history is a feature.

    Never let a GitHub token reach uv or app code

    An app with a private atlanhq git dependency needs a GitHub token for the uv sync or uv lock that clones it. Do not hand it over with git config --global url.<authed>.insteadOf, and do not put it in job-level env:. Both leave the token readable by every later step: tests, pre-commit hooks, conformance series and anything else that imports app code.

    Do not put it in uv's environment either, not even as a GIT_CONFIG_* rewrite on the uv process alone. uv sync and uv lock run PEP 517 build backends and build hooks, and they inherit uv's environment.

    Instead:

    1. Check out the app, then mint the token with the scoped-private-deps-token composite, gated on the caller's opt-in input:
    - name: Mint read-only token for private git dependencies
  id: git-deps-token
  if: inputs.private-git-deps
  uses: atlanhq/application-sdk/.github/actions/scoped-private-deps-token@main
  with:
    app-id: ${{ secrets.FLEET_APP_ID }}
    private-key: ${{ secrets.FLEET_APP_PRIVATE_KEY }}

    The action runs its own copy of git_auth.py repos to list the private atlanhq repositories the app names as git dependencies (every pyproject.toml and uv.lock under project-dir), and mints a read-only fleet App token scoped to exactly that list. When the list is empty it mints nothing: create-github-app-token with no repositories grants the whole installation. The list is also capped by ALLOWED_PRIVATE_DEPS in git_auth.py: a PR controls its own pyproject.toml and uv.lock, so an app naming any other private repo fails closed (repos and mirror both refuse it). Only aggregator repos in AGGREGATOR_REPOS (common-app-server), matched on GITHUB_REPOSITORY, may name any. Never fall back to ORG_PAT_GITHUB, and do not inline these steps again: thirteen inline copies drifted until six had lost their guard (FND-4901). .github/scripts/tests/_scoped_mint.py pins the action and every call. 2. The action fails, naming FLEET_APP_ID and FLEET_APP_PRIVATE_KEY, when the app names a private repository and the token did not mint. Pass require: "false" only where an empty token already fails visibly further on, and say why at the call: an image build (only a Dockerfile that mounts the git_token secret needs it, and that build fails at its clone) or certify (the failed install feeds the verdict, which blocks publish). _scoped_mint.py's NOT_REQUIRED lists every such call. conformance-reusable.yaml still inlines the steps, with the guard: the SDK's own PRs run it, so it can only call the action once the action is on main. 3. Hand the token to a step of its own that runs git_auth.py mirror, and run the fetching command through git_auth.py run in a later step with no token:

    - name: Mirror private git dependencies
  if: inputs.private-git-deps
  env:
    GIT_TOKEN: ${{ steps.git-deps-token.outputs.token }}
    PRIVATE_GIT_DEPS: "true"
  run: python3 path/to/git_auth.py mirror

- run: python3 path/to/git_auth.py run -- uv sync

    mirror mirror-clones each private repository into $RUNNER_TEMP/git-mirrors (a bare git clone --mirror runs no repository code, and git keeps the remote URL as written, so the token is not stored in the mirror) and exits. run points those remotes at the mirrors with a token-free rewrite. The split is the point: a build backend can read the environment of every ancestor process (/proc/<pid>/environ), so the token must not be in the env of the step that starts uv, not only out of uv's own env. run refuses to start when GIT_TOKEN is set. A composite takes the token as its git-auth-token input and does the same inside (setup-deps mirrors; later git_auth.py run steps in the job reuse the mirrors).

    An image build is the one place the token reaches caller code: the app's Dockerfile reads the git_token BuildKit secret. That token comes from the same composite, so it is scoped to the repositories the app names, and absent when it names none.

    Only the first install needs the token. Once it has populated the uv cache and venv, later uv sync, uv run, uv lock --check and even a re-lock of a stale lock fetch nothing. uv run --isolated and a re-resolve on a cold cache do fetch, so give them the token too, through git_auth.py.

    Used by tests-reusable.yaml's tiers (unit, integration, e2e), checks-reusable.yaml, conformance-reusable.yaml, release-version-bump.yaml and the certify gate in build-and-publish-app.yaml (see docs/standards/app-certification.md). test_private_git_deps_wiring.py pins the shape (FND-4740).

    A job's one checkout is the one that counts

    Rule: a job that checks its repo out before setup-deps, or before a composite that wraps it (connector-unit-tests, connector-integration-tests), passes checkout: "false". A job that passes it has an unconditional checkout at the workspace root before that step. unit-tests and sdr-e2e always pass "false": their callers have to check out first anyway.

    setup-deps used to check the repo out again on every call, without persist-credentials: false. The second checkout wrote the job token back into .git/config for the PR code that the tests run next, even where the job's own checkout had declined to, and its git clean wiped whatever the job had put in the workspace. Both of setup-deps' checkouts now set persist-credentials: false. The input still defaults to "true", so a fleet caller that relies on setup-deps to check out is unchanged. lfs: "true" checks out regardless: that checkout is how the LFS objects arrive, and a later git lfs pull would have no credential to fetch a private repo's objects with.

    .github/scripts/tests/test_setup_deps_checkout_wiring.py checks every workflow job's call site against the rule (FND-4900).

    A fleet App token that fails to mint fails the job

    Rule: a Mint fleet App token step has no continue-on-error, and its token is never combined with ORG_PAT_GITHUB (no steps.app-token.outputs.token || secrets.ORG_PAT_GITHUB, in either order).

    # WRONG — a broken App credential silently runs on the org-admin PAT
- name: Mint fleet App token
  id: app-token
  continue-on-error: true
  uses: actions/create-github-app-token@<sha> # v3
- uses: actions/checkout@<sha>
  with:
    token: ${{ steps.app-token.outputs.token || secrets.ORG_PAT_GITHUB }}

# RIGHT — the mint step goes red and names the problem
- name: Mint fleet App token
  id: app-token
  uses: actions/create-github-app-token@<sha> # v3
- uses: actions/checkout@<sha>
  with:
    token: ${{ steps.app-token.outputs.token }}

    The fallback hid every App credential failure behind the broader credential, so nothing ever went red, and the PAT could not be revoked because no one could tell which runs still depended on it (FND-4652). A caller without FLEET_APP_ID / FLEET_APP_PRIVATE_KEY now fails at the mint step; the fix is secrets: inherit. The reusables still declare both secrets required: false, so an omitting caller gets that red step rather than a startup_failure with no check run.

    A job that also runs on fork or Dependabot PRs, which get no Actions secrets, skips the mint for both (head.repo.fork != true and user.login != 'dependabot[bot]') and hands the consumer github.token on those runs (see sdk-tests-reusable.yaml). Never the PAT.

    Out of scope: GHCR login and push still use ORG_PAT_GITHUB, because fleet packages are org-level and the App only has repo-level Packages permission. The scoped git-deps-token / image-git-token mints stay continue-on-error: they have no PAT fallback, and the install or build that needs the token fails when it is empty. test_app_token_fails_closed.py pins all of this.

    A fleet App token asks for what it uses

    Rule: every create-github-app-token step sets at least one permission-* input, and a step that sets owner also sets repositories.

    # WRONG — every permission the App holds, on every repo in the installation
- uses: actions/create-github-app-token@<sha> # v3
  with:
    app-id: ${{ secrets.FLEET_APP_ID }}
    private-key: ${{ secrets.FLEET_APP_PRIVATE_KEY }}
    owner: atlanhq

# RIGHT — the repos and permissions the job's API calls need
- uses: actions/create-github-app-token@<sha> # v3
  with:
    app-id: ${{ secrets.FLEET_APP_ID }}
    private-key: ${{ secrets.FLEET_APP_PRIVATE_KEY }}
    owner: atlanhq
    repositories: application-sdk
    permission-contents: read

    Without permission-*, the token carries every permission the App holds. With owner and no repositories, it reaches every repo in the installation. Leaving out both owner and repositories scopes the token to the current repo, which is already narrow.

    Metadata read is always granted, so do not list it. List only what the job's calls need: an under-scoped token fails at the first API call it lacks. Name the endpoint behind each permission in a comment on the mint.

    A job that only learns its repos at run time, such as a fleet dashboard, may omit repositories. It then needs an OWNER_WIDE entry that says why. A read-only one also gets an entry in READ_ONLY_FLEET, which pins its exact read-only permission set. Mints that predated this rule are listed in UNSCOPED_PERMISSIONS. That list only shrinks: scope the mint, then delete its entry. test_app_token_scoping.py enforces all of this (FND-4902).

    Renovate release freeze

    Renovate PRs do not merge into application-sdk main while a release train is in flight (FND-4175). A Renovate merge moves main. release.yaml then re-renders and force-pushes bump-version-main (the SDK renders chore commits in its notes, so every merge changes the bump branch). The new head has no gate-check status, so a release gate that was running or had already passed starts over.

    Freeze on. A train starts with the first /gate-check on a bump PR and runs until that PR closes. While any open bump-version* PR (main, conformance or contract-toolkit) has a train running, the Renovate auto-approve gate withholds the atlan-ci code-owner approval (condition i in .github/scripts/renovate_approval_conditions.py). The gate counts a train if either of these is true: the head has a gate-check status (any state), or the PR has the /gate-check sticky comment from github-actions[bot]. The comment is what keeps the train alive across a push. The status belongs to one commit, so a merge that slipped past the freeze would re-push the bump branch and lift the freeze. The comment is edited in place and survives every push. A refused /gate-check also writes the comment, so it starts a train too. Without that approval the PR cannot merge. It keeps auto-merge armed, and its log says release train in flight (#N) — holding. An open bump PR on its own does not freeze anything. A new one opens on the first merge after every release, so it is open nearly all the time.

    Freeze off. When a bump PR closes (its release merged, or someone closed it), renovate-release-thaw.yml dispatches renovate-auto-approve.yml once for each open renovate/ PR. The gate re-checks every condition, the freeze included. Held PRs that are still green are approved and merge as usual. If another bump PR's train is still running, nothing is dispatched; that train's own close thaws them.

    If a dispatch fails, it is retried once. If it fails again, the thaw run goes red. Re-run it: it re-dispatches every open Renovate PR, and the gate never approves the same commit twice. To abandon a train without releasing, close the bump PR (the next merge opens a fresh one), or set the override to off.

    Manual override: the repo variable RENOVATE_RELEASE_FREEZE.

    Value Effect
    unset / auto follow the release train (default)
    off never freeze, e.g. when a release is stuck and a dependency fix must land
    on always freeze, e.g. for a release that does not go through /gate-check

    Any other value freezes and logs a warning. After you clear on, dispatch renovate-auto-approve.yml per held PR, or wait for their next CI run. A human approval always bypasses the freeze. The freeze only withholds the bot's approval.

    Scope. Only repos whose ruleset requires the atlan-ci approval are frozen, which today means application-sdk alone. Fleet repos retired the auto-approve caller (bootstrap RETIRED_FILES), so their Renovate PRs merge on required checks alone. A Renovate PR that was approved and queued just before /gate-check can still land; the freeze closes the approval, not the queue.

    Renovate post-upgrade commands

    Three run today, all installed as bare PATH commands by .github/workflows/renovate.yaml and all declared in renovate-config/default.json:

    command lane what it does
    renovate-pkl-sync app-contract-toolkit re-resolves the Pkl lock and regenerates contract artifacts with regenerate_tree, the one regeneration the freshness gate and regenerate_contract.py also use (certify's contract-drift check still runs poe generate until FND-4244 moves it onto regenerate_tree); commits everything it changes under fileFilters and warns about anything outside them (FND-4736)

    The lanes are disjoint by design (FND-3481). "update atlan framework dependencies" is the only lane that moves atlan-application-sdk, atlan-application-sdk-conformance, app-contract-toolkit and their generated outputs. Lock maintenance moves only third-party packages, and it also holds back the transitives a first-party release drags along, so normally the two PRs never edit the same lines whichever merges first. Two cases can still overlap: the replay that finds those transitives fails, or a held transitive moves anyway because its hold is an upload-time ceiling, not a pin. The driver reports both, and the backstop below rebases whatever conflicts. A held first-party package that moves is refused outright (hold-moved). They stay separate PRs on purpose: a third-party bump that breaks an app must not hold up a first-party release. .github/workflows/renovate-rebase-conflicted.yaml is the backstop. Every 15 minutes it dispatches a scoped renovate.yaml run for any fleet repo whose Renovate PR still conflicts.

    Three rules apply to any command added here.

    No ${VARS}. Renovate does not shell-expand post-upgrade commands, so a variable is passed through literally. Everything the command needs must be a literal argument.

    Every command needs a matching regex in allowedCommands in renovate-config/self-hosted.js — an admin-only option, which is why the fleet runs a self-hosted runner at all. A command the allowlist does not match is skipped with a log line and nothing else, so the drift is invisible exactly when it matters: in FND-367 a bound that was not yet allowlisted meant the lock refreshed unbounded and took a package published three minutes earlier, with nothing red anywhere. .github/scripts/check_renovate_allowed_commands.py asserts the preset↔allowlist pairing in CI for that reason. Keep allowlist entries free of character classes and backslashes: a ] truncates the array the guard parses, and "\d" in a JS string literal is just "d".

    Anything that writes a lockfile must leave it valid for every consumer. uv records its resolver settings into uv.lock under [options], and every uv sync --locked compares its own settings against that block — so a bound applied at lock time and left recorded makes the lock unusable in the app Dockerfiles. That is what reddened scan / Build Image fleet-wide in #3212. The bounded driver strips the block; if you add another lock-writing command, check what it records.

    A refused lock refresh is red on purpose, and nothing re-evaluates it

    withhold() in renovate_uv_lock_bounded.py refuses by writing the baseline versions plus a bare [options] table — the one lever the driver holds over a required check, since uv sync --locked then rejects the lock and scan / Build Image holds the branch. Two consequences follow, and both bite:

    Nothing expired it, so the driver stamps why it refused. The branch is not behind its base, so Renovate reuses it without re-running postUpgradeTasks, and the marker committed into uv.lock carries no clock. Observed 2026-08-24: five fleet lock PRs sat frozen for two to four days after the window that blocked them had opened. withhold() now writes the reason on the tripwire's own line (FND-909), which is what lets a machine tell the two kinds apart:

    exclude-newer-span = "P3D"  # refusal: window-empty

    Only window-empty heals on its own — the bound admitted nothing on that pass, which the next slice of window routinely fixes. A broken interpreter, an unsatisfiable floor, a floor that was admitted and still failed, and a yanked-pin rollback are standing faults that waiting never clears.

    A reaper clears the self-healing half. renovate_reap_refused_locks.py runs immediately before Renovate in each repo's matrix job, deletes a stamped window-empty branch on sight, and Renovate rebuilds it in the same pass — recreateClosed: true in the shared preset is what makes that safe. Standing faults keep their tripwire and stay red for a human; recycling a real wedge every four hours would hide it behind a lane that looks busy. An unstamped tripwire is also left alone: "no reason given" must never read as self-healing.

    A window-empty refusal never becomes a PR (FND-3517). These PRs were blocked on purpose and replaced automatically, but they still showed up red and looked like CI failures someone should investigate. The lock lane now sets prCreation: status-success (with internalChecksAsSuccess: true), so Renovate opens its PR only once the branch status is green. Before a PR exists no fleet CI runs on the branch, so that status is just renovate/artifacts, which is the driver's exit code. refusal_exit_code() makes the driver fail only for window-empty:

    Refusal Driver exit PR? What holds it
    window-empty 1 no nothing needed; the reaper deletes the branch, PR or not
    standing fault, tripwire written 0 yes, for a human the tripwire, through the required suite / Conformance Gate
    standing fault, no tripwire written (e.g. an empty uv.lock) 1 no fails closed: with no tripwire nothing required would hold a PR, and a tree matching HEAD would let Renovate commit its own unbounded lock
    any, under --caller-owns-commit 1 unchanged the caller commits nothing

    The reaper deletes with GraphQL updateRefs and beforeOid set to the SHA it inspected, so a push between inspection and delete makes GitHub refuse the delete and the branch is kept. For a branch with no PR it reads history through the compare API, and keeps the branch if that history is incomplete or has any commit not written by the fleet runner.

    A dependency bump that breaks an app's tests still opens a PR: tests only run once the PR exists. Two costs come with it. A good refresh opens one fleet pass (~4h) later, because Renovate never opens a PR on the pass that pushed the commit under status-success. And Renovate may call the merge API on a PR it has just opened, before CI registers, so a repo whose main ruleset requires no checks could merge an untested refresh. Both stay confined to the lock lane: the atlan framework dependencies rules keep prCreation: immediate, and test_renovate_lock_pr_creation.py pins that.

    The fleet dashboard names both, and one of them alarms. conformance.renovate.classify splits the shape out of checks_failing once three things hold — the PR is lock-maintenance, its diff is a uv.lock and nothing else, and that lock carries a lone exclude-newer-span (uv's own [options] always records the absolute exclude-newer beside it, so a lone span is the driver's signature). The stamp then decides which finding it is:

    Finding When Who acts
    bounded_lock_refusal_standing stamped with a reason outside the self-healing set, immediately a human
    bounded_lock_refusal_expired stamped self-healing and older than REAPER_GRACE (two fleet passes), or unstamped and older than the window it names nobody — the reaper should already have taken it

    renovate_refusal_alarm.py runs last in renovate-dashboard.yaml and fails the run on bounded_lock_refusal_expired, because reaching that state means the reaper did not run — and the reaper never fails its own job, so the outage is otherwise silent. Standing faults are printed and never fatal: a wedge a human is legitimately still working through must not red an hourly job, or the alarm stops being read.

    The self-healing vocabulary lives twice — in the driver that writes stamps and in the classifier that reads them — because the driver runs as a bare python3 on the fleet runner and cannot import the conformance package. A test in .github/scripts/tests/ pins the two equal; without it, adding a reason to the writer alone would silently make the alarm stop firing.

    Renovate release-age windows

    The org security baseline (§5) sets a 7-day release-age cooldown. Renovate holds third-party updates for 7 days or 3 days depending on the lane. The 3-day lanes are a deliberate exception to the baseline, recorded here (FND-4651).

    Lane Window Where it is set
    Third-party GitHub Actions, and the toolchains actions/setup-* and astral-sh/setup-uv install 7 days renovate-config/default.json, github-actions release-age rule
    The uv cache-key literal in setup-deps 7 days renovate.json, astral-sh/uv release-age rule
    Local dev images in local/ compose files (major, minor, patch; digests are not held) 7 days renovate.json, local dev images release-age rule
    Third-party PyPI (major, minor, patch) 3 days renovate-config/default.json, PyPI release-age rule
    Lock refresh (lockFileMaintenance), fleet 3 days renovate-config/self-hosted.js, --window P3D
    Lock refresh, application-sdk itself 3 days .github/workflows/renovate-lock-cooldown.yaml, --window P3D
    pkl toolchain 3 days renovate.json, pkl release-age rule
    pre-commit hooks 3 days renovate.json, pre-commit release-age rule

    First-party packages (atlan-application-sdk, -conformance, pyatlan, the app-contract-toolkit, and atlanhq/** actions and reusable workflows) have no window. We publish them, and holding them would hold every SDK fix.

    Why 3 days on the library and tool lanes. The security team confirmed that the detection window they work to is 2 to 3 days. 3 is the conservative end. A longer hold adds no detection time, and it delays the fix in an upstream release that ships before its advisory, because that release looks like any other.

    Why 7 days on GitHub Actions. The exception does not extend to actions. An action runs inside a workflow that holds the org token, so a compromised release reaches a credential on its first run. A library reaches a test environment first. Action majors are also not auto-merged: a human reviews and merges the renovate/major-github-actions PR. Minor, patch and digest bumps still auto-merge once they are 7 days old. The uv cache-key literal follows the same rule for a uv major, so both halves of the bump land in that PR together.

    Regex-managed majors (pkl, the uv cache key, an app's own customManagers) are proposed like any other major. Only the app-contract-toolkit and SDK majors are disabled in the fleet preset, as opt-in migrations (FND-4903).

    What this record is not. It is not a change to the org baseline. Security owns the baseline, and they need to amend it or acknowledge this exception there. Until then, checks/dep-cooldown (from the atlan-security App) keeps enforcing 7 days and reports adoptions aged 3 to 7 days. See What checks/dep-cooldown still reports.

    Changing a window. Change this table first, then every place it names. .github/scripts/tests/test_renovate_release_age_policy.py checks that the configs match the table's windows, and that action majors are not auto-merged.

    The release-age bound on application-sdk's own lock refresh

    postUpgradeTasks reaches every repo in the fleet except the one that publishes the wheel they all install. allowedCommands is admin-only, so post-upgrade commands exist only on the self-hosted runner, and application-sdk's dependency PRs come from Mend. renovate-lock-cooldown.yaml closes that gap (FND-376) by running the same driver from the other side: triggered by the push Mend makes to renovate/lock-file-maintenance, correcting the lock in place before the PR merges.

    Three things about that position differ from the fleet's, and each is a way to get it silently wrong:

    The baseline is the base branch, not HEAD. Under postUpgradeTasks the refresh is still uncommitted, so HEAD is the pre-refresh lock — which is why that is the driver's default. Here Renovate has already committed it, so HEAD is the unbounded lock, and using it would derive every retention ceiling from the releases the bound exists to exclude. The bound would apply, report success, and change nothing. Hence --baseline-ref origin/<default-branch>, which also makes "never roll back what main ships" structural: the driver's rollback gate then compares against main by construction.

    One lock for the whole tree. packages/conformance is a member of the root uv workspace (FND-4671), so the root uv.lock covers it and the bound runs once, exempting only pyatlan. The workspace never resolves atlan-application-sdk from PyPI: it is the workspace root, so conformance's tests run against the tree they ship beside (FND-4256) and there is no registry SDK for the bound to hold. The workspace source is not published metadata: the released conformance wheel still declares a plain atlan-application-sdk[sql] test extra. Until FND-4671 the package carried a second lock that re-resolved the SDK through that extra, and every SDK dependency change had to relock it too.

    One commit, not one per file. Every push to the branch re-fires the PR's entire required-check suite, so the bounded lock and, when pyatlan moved, the regenerated relationship table land in a single commit.

    The workflow pushes with a minted App token, not GITHUB_TOKEN: a GITHUB_TOKEN push does not re-trigger the PR's required checks, which would leave the PR green against a commit that is no longer its head.

    The job runs only for a push made by one of the Renovate identities the approval gate also accepts as PR authors (RENOVATE_AUTHORS), pinned to that list by a drift test rather than copied. Treat it as defence in depth and not as a control: it is evaluated from the workflow file at the pushed ref, so it constrains what runs by accident, not what runs by intent. Restricting who may push a branch is branch configuration and lives outside the repo.

    Any bot commit on a Renovate branch loses renovate/artifacts

    Commit statuses are per-SHA and Renovate stamps only the commits it authors, so the moment an in-repo workflow adds a commit the head moves off the stamped SHA. Condition (f) of the approval gate reads an absent renovate/artifacts as not-green — correctly, since a post-upgrade command that was skipped and one that ran clean are otherwise indistinguishable — so approval is withheld and stays withheld. This is not new and not hypothetical: on #3216 atlan-ci posted three approvals, each dismissed by the next push, and the PR merged on a human's approval after the since-removed requirements sync added the last commit.

    carry_artifact_status.py closes it for this lane by republishing the state it reads from our commit's parent, and only when that state is success. A failure, a pending, an absent context, or an unreadable one all publish nothing and leave the gate withholding. It waits briefly for an absent context before giving up, because Renovate pushes the branch before it sets its statuses and "not yet" would otherwise read as "never".

    If you add another workflow that commits to a Renovate branch, it inherits this problem. Carry the status or accept that the PR needs a human.

    One implementation for both fix-up lanes

    A toolchain pin is declared once, in a file consumers can read

    Rule: a tool version that CI installs gets exactly one literal in the repo, in a file that is also reachable by whoever has to reproduce what CI did. Every workflow, action and script derives it from there; none restates it. Two pins exist today and both follow this:

    Tool Declared in Read by CI via
    Container Python the golden base tag in Dockerfile .github/scripts/container_python_version.py
    pkl PKL_VERSION in application_sdk/pkl_version.py .github/scripts/pkl_version.py

    Why one literal. pkl was pinned in six places at once — install-pkl, the regenerate-contract action, the freshness gate, and three contract-toolkit-* workflows — with nothing keeping them in agreement. Six copies of a value is six chances to bump five.

    Why readable matters more. The freshness gate's whole value is that a local uv run poe generate predicts it. pkl is a language, so a contract can render cleanly on a developer's 0.32.x and be structurally incapable of rendering on CI's 0.27.2 (Invalid character escape sequence on a backslash line-continuation inside a multi-line string, valid from 0.28 on). With the pin buried in a reusable workflow, "it evals locally" was not evidence, the failure surfaced only after push, and the gate's message blamed stale artifacts — FND-1864. No app could even fix it; the version was not theirs to see.

    So the pin lives in the shipped package, which every connector already depends on, and the SDK hands out the exact build:

    python -m application_sdk.dev.pkl print-version   # what CI renders with
python -m application_sdk.dev.pkl path            # download + cache that build
python -m application_sdk.dev.pkl check           # has my PATH pkl drifted?

    The mechanics, when you add the next pin.

    1. Declare the literal in one file, on one line, plainly enough for a regex to read (a Renovate custom manager rewrites it in place).
    2. Add a .github/scripts/<tool>_version.py with a resolve --requested subcommand, and default every workflow/action input to "" rather than to the version. "Empty means the pin" is conditional logic, so it belongs in the tested script, not the install shell — see the first section of this file.
    3. Resolve from the action's own checkout, not the caller's workspace: a composite that runs in a consumer repo has no copy of this repo's source. ${{ github.action_path }}/../../.. is this repo's root in both places.
    4. Put the declaring file in whichever sdk-gate.yaml path filter runs the job that would catch a bad bump. For pkl that is the toolkit filter, whose suite regenerates every contract-toolkit/examples/ tree and fails on any diff — the only check that can prove a pin bump is output-neutral. Skip this and the bump is a one-line change that matches no filter and merges unverified.
    5. Guard it: .github/scripts/tests/test_pkl_version.py fails the build if any workflow, action or script spells a pkl version out, if a call site pins one, if the textual and imported reads disagree, or if the declaring file falls out of that path filter.

    Connector test tiers run on the container Python (FND-4611)

    Reusing scripts from a reusable workflow

    A uses: reusable workflow does not bring its own repo's files into the caller's checkout. To run an SDK script from a reusable that other repos call, sparse-checkout it into a side path and invoke from there:

    - uses: actions/checkout@<sha>   # consumer repo (the working tree the script acts on)
- uses: actions/checkout@<sha>   # SDK scripts, into a side path
  with:
    repository: atlanhq/application-sdk
    ref: main
    sparse-checkout: .github/scripts
    sparse-checkout-cone-mode: false
    path: .sdk-scripts
- run: python3 .sdk-scripts/.github/scripts/<driver>.py ...

    The driver runs from the consumer's working directory, so it acts on the consumer's files; .sdk-scripts only holds SDK code and must never be staged.

    The ref is main or job.workflow_sha, nothing else

    Rule: every actions/checkout of repository: atlanhq/application-sdk in .github/workflows/ uses one of two refs.

    • ref: main is the default. Every consumer calls these reusables @main, so main is the SDK version the fleet runs. It has two properties worth keeping:
    • A re-run picks up a script fix. GitHub re-runs a reusable at the commit it first resolved, so a job.workflow_sha checkout re-runs the old script even after the fix merges. That matters most for the release bump and tag-and-release, which run on a PR closing and have no other trigger.
    • A caller pinned to some other ref of the reusable still gets main's scripts, so a stale pin drifts towards main rather than becoming a self-consistent fork of the SDK's CI.
    • ref: ${{ job.workflow_sha }} (the commit of the workflow file that defines the job) is for checkouts that must match their own YAML exactly. That means a reusable this repo's own PR CI runs, where a PR has to test its own copy of a driver rather than main's. It also covers the scoped private-dependency token mint's git_auth.py. Both were already pinned. actionlint (≤1.7.12) does not model job.workflow_sha, so each file that uses it carries the property "workflow_sha" is not defined ignore in .github/actionlint.yaml.

    Ruled out:

    • A caller-supplied ref. An input that picks the SDK ref is a pinning knob, and pinning is what the fleet is moving away from. sdk_scripts_ref (on commits.yaml, release-version-bump.yaml and tag-and-release.yaml) and sdk_ref (on conformance-upload-sarif-reusable.yaml) are still declared so callers that pass them keep validating, and are ignored (FND-4905). No caller in the fleet passed either.
    • An omitted ref. It resolves to main today, but the reader cannot tell that was meant.
    • Any other expression, above all github.job_workflow_sha (below).

    A deliberate exception carries # sdk-checkout-ref-exempt: <why> inside the step and is listed in the guard. The only one is tests-reusable.yaml's report-to-sdk callback checkout, whose application-sdk-ref is set by this repo's own cross-repo dispatch so an SDK PR tests its own callback scripts.

    .github/scripts/tests/test_sdk_checkout_ref_pinning.py enforces all of this.

    Not github.job_workflow_sha

    ${{ github.job_workflow_sha }} is documented in the github context as the commit of the reusable workflow file the caller resolved. It renders empty. It is an OIDC token claim, not a usable expression value. The property that works lives on job, not github.

    The failure is silent and the wrong way round: actions/checkout treats an empty ref as not supplied and takes the default branch, so the step goes green having fetched a different commit's script than the workflow the caller pinned. FND-372 hit this; it only surfaced because the script did not exist on main yet, so the next step died on a missing file.

    Generalising: never let a with: value that must not be blank come from an expression that can evaluate to empty. When verifying a change to a workflow like this, read the checkout step's logged ref: rather than concluding from a green tick.

    System packages go through one script

    Rule: a package list a caller supplies reaches apt-get install only through .github/scripts/install_apt_packages.py. The script takes the list from an environment variable (--env APT_PACKAGES) or a file (--file .github/ci-system-deps.txt), checks every whitespace-separated token is a plain Debian package name ([a-z0-9][a-z0-9+.-]*), and only then runs apt-get update and apt-get install -y --no-install-recommends with the packages as argv. A rejected or empty list installs nothing and fails the step.

    The same list has three input names and a file, and all of them go through it:

    Where it is declared Installed by
    apt-packages (tests-reusable.yaml, one job in each tier; conformance-reusable.yaml) --env APT_PACKAGES
    apt_packages (build-and-publish-app.yaml, certify and certify-unit) --env APT_PACKAGES
    system_deps (checks-reusable.yaml) --env SYSTEM_DEPS
    .github/ci-system-deps.txt (bootstrap --system-deps) conformance-reusable.yaml, --file, before the D series

    The input names stay as they are; renaming one breaks every caller that passes it.

    Why: before FND-4908 the check was a grep copied into six steps, pinned together by byte-identity tests, and three sites (system_deps and both readers of ci-system-deps.txt) installed the value unchecked. One app could declare the same list three ways and get a different answer from each.

    How the script reaches the step: from this workflow's own commit, like any other driver (see Reusing scripts from a reusable workflow). tests-reusable.yaml's tiers and checks-reusable.yaml sparse-check it out into .sdk-apt and remove it after the install; build-and-publish-app.yaml reads it from its existing sdk/ checkout; conformance-reusable.yaml fetches it with the lock-check scripts and copies it to $RUNNER_TEMP.

    Not in the vendored detect action. run-conformance-detect is copied into every consumer by bootstrap and only changes when that repo re-runs it, so it installs nothing; conformance-reusable.yaml installs ci-system-deps.txt before calling it. A consumer whose vendored copy still has the old xargs step re-installs a list the reusable has already checked, or never reaches it because D is skipped after a rejected one.

    .github/scripts/tests/test_install_apt_packages.py tests the script and fails on any apt-get install in .github/workflows, .github/actions or the bootstrap templates that bypasses it. It reads whole shell commands, joining backslash-continued lines, so splitting apt-get \ from install "$LIST" does not hide an install. The only exceptions are fixed packages this repo names itself (twingate, openconnect), listed in that test. Each apt-get call the script makes is bounded (TIMEOUT_S), so a stalled mirror fails the step instead of holding the job.

    Self-references are @main

    Rule: every uses: of this repo's own actions and reusable workflows — atlanhq/application-sdk/.github/actions/<name>@… or atlanhq/application-sdk/.github/workflows/<file>@… — names @main. That holds in workflows, composite actions, workflow templates, the conformance bootstrap templates, and the usage examples in comments and READMEs. No release tags, no commit SHAs.

    Why @main and not the release tag: the fleet already calls us at @main (1421 references across 605 active org repos when FND-4249 measured it; the bootstrap templates scaffold @main). A mixed policy is the worst of both: a consumer pinning tests-reusable.yaml@vX still got composites from main, while sdr-e2e called setup-deps at a release tag, so one job ran two revisions of this repo. Rewriting every self-reference to the tag on each release would only help consumers who pin tags, and none of the fleet does.

    How it fits SHA pinning: third-party actions are still SHA-pinned, and conformance rule C001 still enforces that. C001 has always exempted atlanhq/ refs whatever the ref, because they are meant to track @main (packages/conformance/conformance/suite/rules/ci.py; the exemption is pinned by packages/conformance/tests/test_actions_pinning.py). This rule tightens that exemption for this repo's own refs: C001 accepts any ref, and this rule accepts only @main.

    Why it stays put: Renovate's github-actions manager tracks @vX.Y.Z and SHA refs but leaves a branch ref alone. A tag-pinned self-reference gets bumped on every release (that is how sdr-e2e drifted); @main never does.

    What it costs: an action change reaches every consumer's next run, and an input added on a feature branch is ignored until it merges (callers resolve @main). Two consequences are already written down elsewhere: an action must not assume the consumer's pinned SDK has a module that only a newer release ships, and logic that has to be testable before merge belongs in a .github/scripts/ driver checked out at job.workflow_sha, not in a new composite.

    .github/scripts/tests/test_self_reference_pinning.py enforces the rule and also fails on a self-reference to an action or workflow that no longer exists, so deleting a reusable without cleaning up its callers and examples is red.

    Superseded reusables are deleted, not kept "for compatibility", once a clone of the org's active repos shows no caller (code search misses repos). FND-4249 removed build-apps-image.yaml and publish-app.yaml (replaced by build-and-publish-app.yaml), e2e-full-reusable.yaml (folded into tests-reusable.yaml), and the ae-stack-up composite on that basis. It also removed the ae-workflow composite and its ae-workflow-register.yaml wrapper, whose single consumer had pinned them to a commit and not run them in five months.

    Retiring a reusable that a bootstrap shim called

    Rule: when bootstrap retires a shim (RETIRED_FILES in packages/conformance/conformance/bootstrap/render.py), the application-sdk reusable that shim called stays until C002 reports zero copies of the shim across the fleet. Delete the reusable after that, never before, and in the same PR add it to DELETED_RETIRED_REUSABLES with the C002 count (date and source).

    Why: bootstrap removes a retired shim from a consumer repo only when that repo next runs it, so copies linger for weeks. Each copy calls the reusable at @main. Once the reusable is gone, every trigger of that copy fails at startup: no jobs, no logs, a red run. The auto-fix-vulnerabilities.yaml reusable was deleted (#4717) while 8 app clones still carried auto-fix.yml, and those apps fail on every PR comment until they resync.

    Enforced by: .github/scripts/tests/test_reusable_retirement.py. Every retired workflow must be listed in RETIRED_SHIM_REUSABLES (with the reusable it called) or RETIRED_SHIMS_WITHOUT_REUSABLE. A reusable named there must still exist and declare workflow_call, unless DELETED_RETIRED_REUSABLES records its deletion as a ReusableDeletion with c002_copies=0, an ISO counted_on date and a source. PREMATURE_REUSABLE_DELETIONS holds the one deletion made without that count (auto-fix-vulnerabilities.yaml); the test pins it to that entry, so it cannot be used to skip the count. test_self_reference_pinning.py cannot catch this case: once the shim template is gone, nothing in this tree calls the reusable.

    The test cannot read the fleet. The C002 count is the evidence a reviewer checks against the deletion record.

    Consumers stay on @main, not a moving major tag

    FND-4654 counted 886 consumer references to our reusables across the local app clones; 869 were @main. A moving major tag (@v3) would let a breaking edit to tests-reusable.yaml or build-and-publish-app.yaml land on main without reaching 65+ repos in the same minute. We are not adopting one:

    • It protects nothing inside the reusable. Composite actions and checkouts inside our reusables resolve @main (see "Self-references are @main"), so a tagged reusable still runs main's composites.
    • Every consumer ref would have to be rewritten, and moving the tag on each release is one more release step that can be missed.
    • The failures we have actually had came from retirement order, which the rule above fixes, not from edits reaching consumers too quickly.

    Breaking edits to a reusable go through the same path as any other: keep old inputs working until callers move, and test on a consumer before merge.

    tests-reusable.yaml calls its tiers (FND-4676)

    tests-reusable.yaml is the only connector test workflow a connector calls. It owns every input and secret declaration, routes the run, and aggregates the verdict. The tiers live in three workflows it calls, each at @main:

    Workflow Jobs
    tests-reusable.yaml queue-proof, detect-merge-queue, detect-integration, discover-e2e, wake- / pause-dataforge-source, report-to-sdk, scorecard, renovate-artifacts, tests-passed (Tests Gate), and one caller job per tier
    unit-tests-reusable.yaml unit, detect-api-member, api-member
    integration-tests-reusable.yaml integration
    e2e-tests-reusable.yaml build-e2e-image, merge-e2e-image, sdk-head-recheck, lease-tenant, prepare-tenant, e2e, release-tenant

    The rules at the seams, all pinned by .github/scripts/tests/test_tests_reusable_split.py:

    • Inputs are declared once. A tier input is required: true with no default, and the caller job forwards it from the tests-reusable.yaml input of the same name. A forgotten passthrough fails at parse time instead of taking a second default. The one exception is the integration tier's timeout-minutes, whose literal default test_job_timeouts.py reads.
    • The caller job declares the tier's permissions, exactly the strongest level each scope is used at in that tier. A called job can only narrow its caller's grant, so a scope missing there arrives as none.
    • The gate reads each tier job's result as a tier output (jobs.<id>.result, which actionlint 1.7.12 does not model; see .github/actionlint.yaml). Outputs are empty when the caller job was skipped, cancelled or failed at startup, so every read falls back to the caller's own result: needs.e2e.outputs.lease-tenant-result || needs.e2e.result. A cancelled tier never reads as a pass.
    • A tier job never names a tests-reusable.yaml job. needs.<job> cannot resolve across the call and renders empty. Discovery's outputs reach the e2e tier as inputs (e2e-matrix, e2e-cloud-*), and the conditions every e2e job used to repeat (discovery succeeded, at least one suite) are the e2e caller job's if:.

    Two consequences to know:

    • Check names gained a segment: tests / unit / Unit, tests / integration / Integration, tests / e2e / End-to-end (<leg>). Nothing in the fleet requires them; every ruleset requires tests / Tests Gate, which did not move. test_command_comment.py matches the leg suffix, so the /e2e table is unaffected.
    • Piloting a tier change needs two edits. A connector pointed at a tests-reusable.yaml branch still runs main's tiers, because uses: cannot take an expression. To pilot a change to a tier, also point that tier's uses: line in tests-reusable.yaml at the branch, on the pilot branch only. test_self_reference_pinning.py fails that branch, which is what keeps it from merging.

    concurrency: is not a lock, and not a queue

    Rule: never use a concurrency: group to protect a shared external resource (a tenant, a fixed environment, a singleton deployment). Use it only to supersede or de-duplicate runs of the same thing.

    Two independent limits make it unfit as a lock:

    • It is per-job. The group is released when the job ends. Anything the job set up for later jobs to use — an install, a seeded database — is unprotected from the moment that job finishes.
    • It holds ONE pending run. cancel-in-progress: false reads like a queue but is a waiting room with a single chair. A third arrival does not wait: it evicts the run that was waiting, which is reported as cancelled having never been given a runner, so there is no log blob at all (gh api .../jobs/<id>/logs → 404). A few-second job lifetime with no logs is the signature.

    That combination caused FND-218: batching more than two PRs into the merge queue self-inflicted roughly a two-in-three ejection rate, and because the connector callback mirrored cancelled as failure, it read on the dispatching PR as "your change broke the connector".

    Do not key a group on github.ref for anything a merge queue or a cross-repo dispatch can reach. On a cross-repo workflow_dispatch, github.ref is the callee's ref — always refs/heads/main — never the dispatching commit. So a ref-keyed group collapses every concurrent dispatch into one group, and the one-pending-slot rule then evicts all but two. Key on github.run_id off the PR path:

    concurrency:
  group: thing-${{ startsWith(github.ref, 'refs/pull/') && github.ref || github.run_id }}
  cancel-in-progress: ${{ startsWith(github.ref, 'refs/pull/') }}

    On a real PR ref the shared group is the point (supersede the previous commit); everywhere else the run must be independent.

    For a shared resource, take a lease instead. The (app, cloud) tenant lease in e2e_tenant_lease.py is the worked example (FND-250). It needs no lock server:

    • One ref per resource, with a fixed name: refs/e2e-tenant-lease/<app>/<cloud>/holder. POST /git/refs on a name that already exists returns 422, and that is an atomic test-and-set evaluated by GitHub — of N simultaneous callers exactly one gets 201. That 422 is the lock, not an error path bolted onto one.
    • The ref points at a blob holding the holder's identity (run id, attempt, acquisition time). A ref can target a blob, which is what lets a single atomic creation both take the lease and record who took it. Waiters read it to tell a live holder from a dead one.
    • Liveness is the holder's run status, not a heartbeat. A lease whose run is completed is reaped by whoever notices. This is the part if: always() cannot do: GitHub cancels queued jobs rather than running them, so a cancelled run's release job never starts.
    • Release must check ownership first. A fixed name is a name you can delete someone else's lease with.

    Release cannot be made fully atomic, and that is an accepted trade-off, not an oversight. The check-then-delete above is inherently racy: the refs API offers no conditional delete, so between the final ownership read and the DELETE a replacement holder can acquire the ref, and the delete would take the new holder's lease. The implementation re-reads the target immediately before the delete, which narrows the window to one round-trip but cannot close it. The deliberate decision is to rely on the TTL as the load-bearing bound rather than chase a stronger primitive: the only interleaving that loses is a TTL breaking a lease whose run is still live, and sizing the TTL above the longest legitimate hold makes that window unreachable in practice. The alternative — deleting only via a storage/API primitive that supports delete-if-current-target — does not exist on git/refs, so proactive release stays best-effort and the next acquirer's reaping of completed holders is the actual safety net.

    Do not build exclusion out of an ordering rule. The first version of this lease was an ordered queue: every run created a ticket ref named after itself, and the lease belonged to whichever live ticket sorted lowest by (run_id, run_attempt). It failed on its first concurrent run — both contenders acquired and both installed onto the same tenant. Two reasons, and both generalise:

    • run_id increases with run creation, which is not the order runs reach a given job. In the observed failure the lower-id run got there 15 seconds later.
    • A total order gives FIFO fairness, not exclusion. A run that checks only the tickets ordered ahead of it never notices that a run behind it already holds the lease.

    Ordering-based exclusion is only sound if every contender's ticket exists before any contender decides, and nothing enforces that. Use an atomic primitive and derive nothing from ids. The cost is fairness — acquisition becomes a scramble, so bound starvation with the wait budget below rather than with a queue position.

    But when one run needs SEVERAL of these locks, it must take them in a fixed order — and that is a different rule, not a contradiction of the one above. The lease job used to be a per-cloud matrix that acquired every cloud's lease in parallel and held each for the whole run while blocking on the rest. That is textbook hold-and-wait, and it deadlocked the first time two runs queued behind one holder (FND-646): the holder released all three leases at once, the two waiters raced for the freed set and split it — one took aws + azure, the other gcp — and each then blocked on what the other held for the whole 90-minute wait budget. Any time two or more runs are queued behind a holder, a parallel matrix makes that split the expected outcome, not a rare interleaving.

    The fix is resource ordering: one job takes every lock it needs, one at a time, in an order that is a pure function of the resource names (sorted()). Two runs can then never hold locks the other needs out of order, so the worst case degrades from mutual blocking to plain serialisation. Note what is and is not being ordered — the CAS still grants every lease, and the order governs only the sequence in which one run takes several of them. That is why this does not re-open the rejected-ordering trap above.

    Consequences worth spelling out:

    • The wait budget becomes a total across the set, not per resource, or N locks can outlast the job timeout by N times over and the runner's bare "cancelled after Nm" replaces the actionable error.
    • Acquisition has to be all-or-nothing: a run that cannot get the whole set hands back what it took, immediately, rather than waiting for its cleanup job.
    • Derive the order from the names only. Run id, arrival order, or the caller's list order all make two contenders disagree about which lock comes first, which is the entire guarantee.
    • Release can stay parallel. It cannot block, so there is no wait to order.

    Three further consequences to design for:

    • A waiting run occupies a runner, so give the wait a budget and fail loudly past it, naming the holder. A contention outcome must never be phrased as a test failure.
    • Ref writes need contents: write, so put acquire/release in their own small jobs and leave the jobs that execute test code read-only.
    • A fail-open is only a fail-open if every consumer downstream agrees. This lease used to warn and return disabled when it could not write refs, on the reasoning that failing an ungrantable lease would turn a safety improvement into a fleet-wide red. It did not proceed: the install job verifies its own tenant's lease before installing, needs only contents: read to do it, finds nothing, and reds — so the run went red anyway, two jobs later, with an error saying "re-run this job" when re-running could not help (FND-702). The posture was not being chosen; it was being reversed by a consumer, at the cost of the one message that could have explained it. Before writing a fail-open, walk every consumer of the thing you are failing open on and check that it tolerates the degraded value; if any one of them does not, the fail-open is fiction, and the honest version is to fail where the cause is still in hand.

    The ref transport lives in exactly one module, and that is why the lease is a script and not a composite action. .github/scripts/_gh_refs.py holds the primitives — the CAS, the blob read/write, the ref listing, holder liveness, and the 403-rate-limit/403-permission split — and the tenant lease, the DataForge source refcount and the e2e dispatch guard all import it. Callers that disagree about what a transport failure means do not get a copy each: the module raises TransportError, a SystemExit, so the lease and the refcount fail the job as they always did, and the guard, which fails open, catches it by name and dispatches (FND-4925). A composite action cannot import it: it is checked out in isolation, with no sibling scripts on disk, so it has to carry its own copy. The lease was an action, and the copy taken from it for the refcount dropped the rate-limit/permission split on the way out — reintroducing the exact conflation FND-702 had fixed, caught only in review (FND-1992 / FND-2674). If a mechanism needs a primitive that another mechanism already has, a composite action is the wrong container for it.

    That change also closes a second-order problem worth knowing about: uses: cannot take an expression, so an action reference can only ever be @main. A PR that changes an action's driver therefore tests main's copy of it, not its own. Running the driver off the job.workflow_sha sparse checkout the job already needs makes a PR exercise its own version. Contenders still agree, because every consumer calls the reusable workflow @main and job.workflow_sha is the commit that resolves to — the only run where the two differ is the run that is editing the driver.

    An evicted run still reports, and the newest run owns the required check

    A required status check is resolved to the check run of the newest check suite on the commit — not the most recently completed one. Both halves of that sentence are load-bearing, and together they make a same-commit eviction able to block a pull request outright.

    A bot PR receives several pull_request events on one head SHA seconds apart: opened, then one labeled per label the bot applies. A tests.yaml that subscribes to labeled — every scaffold before FND-3839, and every connector repo until it resyncs past it — gets one Tests run per event on the same SHA, and the unit job's ref-keyed group evicts all but one. tests-passed is if: always() — a required context must always report — so each evicted run publishes a failure on tests / Tests Gate. Eviction order is not run-creation order, so when the surviving run is not the highest-id one, its success does not count and the PR sits at mergeStateStatus: BLOCKED with auto-merge enabled until the bot rebases. Measured on atlan-trino-app (FND-2167): across 18 PRs every merged one had its highest-run-id gate success, and the single PR whose success sat under a cancelled sibling was the blocked one.

    A skipped job is not a silent job. It publishes a check run with conclusion skipped, and GitHub counts skipped as a pass for a required status check. So "skip the jobs on a non-e2e labeled event" does not remove the duplicate runs' verdict — it replaces a false red with a false green from the newest suite, which would override a genuine failure from the opened run and make the gate decorative on exactly the auto-merge path it guards. Only a job that never instantiates reports nothing at all: skipping the caller job leaves the context untouched, so the previous run's verdict stands. Know which of the two you are doing.

    Greening the gate on cancellation is not available either: an un-run test must never green a merge, and a human cancelling the only run would do just that.

    What is left is to re-run the offender: .github/scripts/rerun_evicted_tests_run.py, invoked from tests-passed in the run that did produce a verdict. If a newer run on the same commit concluded cancelled, it is re-run, and its fresh check runs supersede the evicted attempt's on the required context — a measured verdict replacing an unearned one. Four properties that make it safe to leave running fleet-wide:

    • Only the newest run is ever touched. Older evicted siblings publish red rows that are ugly and harmless, and re-running them would put them back in one concurrency group to evict each other again.
    • An eviction is distinguished from a deliberate cancel by duration. An eviction never gets a runner and is over in seconds; a person cancels a run minutes in, and that cancel must stick.
    • One attempt. A candidate already on run_attempt > 1 is left alone, so two runs cannot re-run each other indefinitely.
    • Fail open, exit 0, continue-on-error. The step runs inside the required context; a repair that can redden it would turn a cosmetic flake into the block it exists to remove.

    Re-running needs actions: write, which the reusable's own GITHUB_TOKEN cannot be given — a called workflow may only equal or narrow its caller's grant, the callers grant actions: read, and asking for more is a hard workflow error in every consumer at once. ORG_PAT_GITHUB does the write and its absence is a logged no-op.

    Declare the permissions a reusable workflow needs, in the caller

    A called workflow's permissions can only equal or narrow its caller's, so a job in the reusable declaring contents: write is a ceiling, never a grant. A caller with no block at all satisfies it purely from the repository's default_workflow_permissions — which means tightening that setting, an ordinary hardening step, silently strips the grant from every adopted repo at once, with nothing in the resulting failure pointing at the cause.

    So the canonical scaffolded tests.yaml declares the set explicitly. Two things make that edit easy to get wrong:

    • A permissions: block is exhaustive, not additive. Every scope it omits becomes none. A well-meaning permissions: {contents: read} on the caller is strictly worse than declaring nothing, because it clamps a job whose repository default would have carried it.
    • Derive the set from the reusable, in a test. test_tests_yaml_permissions reads every permissions: block in tests-reusable.yaml and the three tiers it calls, takes the strongest level each scope is used at, and asserts the scaffolded caller declares exactly that — so adding a scope to a job of the reusable fails there rather than silently arriving as none in every connector.

    Collapsing a managed workflow into a reusable renames its status check

    A job that uses: a reusable reports as <caller job> / <called job>, never as the caller job alone. So moving a bootstrap template's body into a reusable renames the check every consumer repo publishes — checks.yml's pre-commit became pre-commit / Pre-commit in FND-1994. Where a repo's ruleset requires the old context by name, that requirement can never be satisfied again and every PR in that repo deadlocks: the required check is simply absent, not failing.

    The rename is unavoidable (there is no spelling of caller and callee that collapses the path), so it is handled rather than dodged:

    • Re-sync one repo at a time and edit its ruleset in the same step. Both halves are per-repo, and neither is a bot action — the fleet App has no workflows: write and no ruleset write.
    • .github/scripts/gate_enforcement_scan.py reports which repos actually pin a context, which is the list this applies to. Most of the fleet pins nothing and migrates with no ruleset edit at all.

    This is also why such a migration is a pull, not a push: a repo keeps running its own inlined copy until it is re-synced, un-migrated and migrated repos coexist indefinitely, and C002 reports the difference at WARN — a signal that the repo is due a re-sync, not a failing gate. What that costs the SDK side is that every parameter the old shape carried must stay readable: see extract_apt_packages, which reads system_deps off both the caller's with: block and a pre-migration inline apt-get install step. Drop the second arm and the first re-sync of an un-migrated repo silently deletes a step its build needs.
